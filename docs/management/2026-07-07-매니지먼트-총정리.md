## 1. 무엇인가 — 한 문장 정의

**"광고 계정을 계속 관찰하다가 이상하면 알려주고, 대화로 상담해서 처방을 만들되, 지출을 늘리거나 게재·과금이 걸린 일은 반드시 사람 승인을 거쳐 단 하나의 실행 경로로만 나가는 자율운영 루프"** 다(지출을 줄이는 중지·감액은 자율 + 알림). ClickMe 핵심 3기능 중 4-2로, 목표·예산·플랫폼·성과를 단일 창구에서 관리한다.

```
                ┌────────── APScheduler 워커 3잡 (이상스캔·주간리포트·리밸런싱) ──────────┐
                ↓                                                                      │
[관측] Meta reader / mock → [감지·진단] 결정론 룰 → 애매하면 LLM 재판정 (diagnose_campaign)
                ↓ findings
[알림] PanelSink 판정표 → management_notifications → SSE → 프론트 벨/패널
                ↓ [상담하기]
[상담] 채팅 세션에 상담 카드 → 옵션 버튼 → CLIO(에이전틱 RAG 어시스턴트)
                ↓ 처방
[제안] 재생성 에이전트 / 캠페인 생성 3갈래 / propose_action → ActionProposal
                ↓
[승인] approval.py — Tier 판정 + 3단계 검증 (Tier 높으면 사람 승인 필수, HITL)
                ↓ ApprovedAction
[실행] Executor — 승인 후 4단계 재검증 + 멱등 실행 + Meta writer (mock/dry_run/live)
                ↓
[기록] 감사 로그 · 멱등키 · automation_runs · 롱텀 메모리(chat_execution_history) ──────┘
```

## 2. 설계 원칙 (전체를 관통하는 불변식)

1. **돈의 단일 경로** — 에이전트든 챗봇이든 라우터든, 지출성 조작은 전부 `ActionProposal`을 만들 뿐이고 Writer에 닿는 길은 `execution/executor.py` 하나뿐이다. LLM 출력이 직접 Writer를 호출하는 경로는 존재하지 않는다.
2. **의도적 이중 검증(defense in depth)** — 승인 전 3단계(`approval.py`)와 승인 후 4단계(executor)는 일부러 중복이다. 승인~실행 사이 시간 갭에 상황이 바뀌는 걸 잡는다.
3. **HITL** — 관측·집계·기록은 워커가 자율로 한다. 집행 write 중 **지출을 늘리거나 게재·과금이 걸린 것(Tier 3)은 항상 사람 승인**을 거치고, **지출을 줄이는 Tier 1(중지·감액)은 자율 실행 + 알림**이다("줄이는 건 자율, 늘리는 건 승인"). 게재 시작(`ACTIVATE_CAMPAIGN`)은 실과금이라 예외 없이 사람 승인.
4. **mock 우선** — `adapters/mock.py`가 reader 포트를 그대로 구현해 API 키 없이 데모 전체가 재현되고, mock↔실연동 전환은 `wiring.py` 한 곳에서만 일어난다.
5. **경계 강제** — A(감지·진단·승인)/B(실행·재생성) 내부 패키지 상호 import 금지, 유일한 접점은 `contracts/`. 타임스탬프 UTC aware, 통화 KRW 정수, 모든 계약에 `schema_version`.

## 3. 폴더 구조와 역할 분담

```
backend/domain/management/
├── contracts/        🤝 계약·enum·포트 — A/B 유일 접점 (변경은 양측 리뷰 + 골든 샘플)
├── adapters/         Meta reader(조회)/writer(집행)/oauth + mock (포트-어댑터, 벤더 격리)
├── detection/        🅰 감지·진단 — 결정론 룰 + agentic_scan(diagnose_campaign)
├── approval.py       🅰 승인 플레인 — Tier 정책표 + 3단계 검증 → ApprovedAction 발급
├── execution/        🅱 실행 — executor 4게이트·멱등키·상태머신·감사 로그
├── agents/           진단 agent(🅰) · 재생성 agent(🅱, 모든 ActionProposal 생산)
├── remediation/      운영 알림 C안 — panel_sink·advisor·consult_service·notification_store
├── assistant/        CLIO 에이전틱 RAG 어시스턴트 (LangGraph ReAct + pgvector KB)
├── comparison/       성과 전후 비교 (시뮬 예측 vs 실측, 환산 금지)
├── evals/            진단 정확도·재생성 품질·KB 충실성 eval (LangSmith)
├── scheduler.py      APScheduler 워커 3잡
└── wiring.py         Composition Root — mock↔실연동 전환 유일 지점
```

역할 분담 원칙은 "agent 1개 + eval 1개 + HITL 한 축씩 각자 소유" — 🅰는 감지·진단·승인(HITL 설계), 🅱는 실행·재생성(HITL 강제). `ActionProposal` 생산자는 🅱 단독, 승인의 뇌는 🅰, 채팅 발화는 오케스트레이터(통합 딥에이전트)만.

## 4. 계약 3종과 파이프라인

```
[진단]              [제안]               [승인 플레인]           [실행기]
관측→tool→진단  →  복구agent→패키징  →  Tier판정→사람승인   →  재검증→멱등→감사
     │                  │                    │                    │
DiagnosisResult    ActionProposal       ApprovedAction        ActionResult
```

`ActionProposal`은 18필드 고정(proposal_id·tenant_id·evidence_metrics·confidence·expected_state_version·budget_before/after·max_total_spend·expires_at·proposal_hash·approval_policy_version 등).

**action_type 8종 × Tier** (`contracts/policy.py TIER_POLICY`, 미등록 타입은 보수적으로 Tier 3 + `UNSUPPORTED_ACTION` 차단)

| action_type | Tier | 설명 |
|---|---|---|
| `PAUSE_CAMPAIGN` | 1 | 게재 중단 (지출↓ = 자율 + 알림) |
| `DECREASE_BUDGET` | 1 | 예산 감액 |
| `INCREASE_BUDGET` | 3 | 예산 증액 |
| `REPLACE_CREATIVE` | 3 | 소재 교체 (재생성 루프) |
| `CREATE_CAMPAIGN` | 3 | 신규 캠페인 생성 |
| `ACTIVATE_CAMPAIGN` | 3 | 게재 시작 — 실과금이라 항상 사람 승인 |
| `EXPAND_AUDIENCE` | 3 | 타깃 확장 (에스컬레이션 1순위) |
| `CHANGE_BID_STRATEGY` | 3 | 입찰 전략 변경 (에스컬레이션 2순위) |

원칙은 **"줄이는 건 자율, 늘리는 건 승인"**. Tier 0(조회)~1 자율, Tier 2(재배분)는 v1 비활성, Tier 3은 건별 사람 승인.

**승인 전 3단계** — ① 만료(expires_at)·proposal_hash 검증 ② 승인자 tenant·계정 권한 ③ 현재 정책 기준 Tier 재판정(라벨과 다르면 재라벨 후 감사).
**승인 후 4게이트** — ④ ApprovedAction 유효성 재확인(만료·정책버전·hash·tenant·tier) ⑤ `expected_state_version` 낙관적 락 비교(불일치=STALE_PROPOSAL) ⑥ 지출 총액 재계산 + 멱등키 선점 ⑦ 감사 로그(재시도·부분 실패 포함).
멱등키는 `sha256(approval_id + action_type + 대상IDs)` — 같은 승인 건은 몇 번을 눌러도 1번만 집행된다.

## 5. 세부 트랙별 요약

### ① 데이터 게이트 (adapters)
Meta Marketing API를 reader/writer로 나눠 포트-어댑터로 감쌌다. org별 OAuth 연결(`meta/oauth.py`, 토큰 AES 암호화 저장, `management_meta_connections`)로 조직마다 자기 광고 계정을 붙인다. writer는 **mock/dry_run/validate_only/live 4모드** — use_mock이면 live가 봉인된다. Meta GET 캐시로 rate limit을 아낀다.

### ② 감지·진단 (detection + scheduler)
2단 구조 — 값싼 결정론 룰(게재0·소재피로·지갑소진·예산페이스·성과미달)이 1차 프리필터, 애매한 것(INCONCLUSIVE)만 LLM ReAct 에이전트가 Meta 신호를 도구로 조회해 재판정한다. 진단이 `diagnose_campaign` 하나로 통일돼 **라우터(화면)·워커(자동 스캔)·수동 점검이 전부 같은 판단**을 쓴다. 판정 임계는 상수 단일원천(기대 노출의 50% 미만 2시간 연속 등)이고 `/run` 응답에 `assumptions`로 기준·출처까지 노출한다. 정상 확인 캠페인은 normals로 내보내 미해결 알림을 자동 해소(reconcile)한다.

### ③ 알림·상담 (remediation + 프론트 벨/패널)
스캐너 findings가 곧장 알림이 되진 않는다. `PanelNotificationSink`가 판정표(무시됨·미열람·쿨다운·dedup)로 스팸을 거르고, 확정 건에만 advisor가 LLM 조언을 붙여 저장 + SSE 발행한다. dedup은 모듈 잠금 + DB 부분 유니크 인덱스(org·kind·dedup_key 미해결 1행) 이중 방어. [상담하기]를 누르면 전이표대로 재검증 후 채팅 세션에 상담 카드를 심고(CAS로 이중 심기 방지), 카드 옵션 버튼은 `option_select`로 지시문화된다(tool_hint는 화이트리스트만 신뢰).

### ④ 처방·제안 (agents/regeneration + 라우터)
진단→처방 매핑은 결정론 코어(`decide_action`), 저확신이면 돈 늘리는 처방을 보류하는 게이트(`decide_with_confidence`)가 얹힌다. 소재가 필요하면 4-3(생성)에 HTTP 위임만 하고, 금지표현 guard 통과 후 사람이 시안을 고르면 그때 제안을 패키징한다(AWAITING_SELECTION → package). **캠페인 생성 3갈래** — 직접 입력(`create-proposal`) · 4-3 시안(`from-candidate`) · 4-1 시뮬 결과(`from-simulation`, 클릭의향률·거부율 집행가능 판정 필요) — 전부 제안→승인→실행 경유.

### ⑤ 어시스턴트 CLIO (assistant)
LangGraph Tool-calling ReAct. 수치는 **live 도구에서만 인용**(환각 방지), 해석·정책은 pgvector KB RAG, 근거 부족 시 자기교정 재검색(CRAG-lite), 최신 정보는 web_search를 advisory로만. 운영 변경은 `propose_action`으로 제안만 하고 승인 필요 Tier면 `interrupt`로 그래프를 멈춰 사람에게 넘긴다. 무키 폴백(키워드 라우팅 + 실시간 툴 요약)으로 키 없이도 동작. eval(진단·환각·충실성·검색)이 `evals/`에 동봉.

### ⑥ 워커·기록 (scheduler + core/automation)
APScheduler 3잡(이상스캔·주간리포트·리밸런싱 제안)은 **기본 off, `MANAGEMENT_SCHEDULER_ENABLED`로 opt-in**, 잡 실패가 스케줄러를 죽이지 않게 격리한다(다만 실패도 `automation_runs`에 `status=error`로 남아 관측 가능 — 연속 실패 임계·알림·dead letter는 v1 범위 밖). 결과는 3도메인 공용 `automation_runs`(dedup 유니크)에 쌓이고, 실행 확정 건은 `chat_execution_history`(롱텀 메모리)에 남아 어시스턴트가 과거 조치를 회상한다. 리밸런싱은 제안만 만들고 실행(budget-commit)은 사람 승인을 그대로 거친다.

### ⑦ 성과·예산·자동화 부가 기능
- **CVR·ROAS 재정의** — 전환=리드/가입/설치 일반화, ROAS=전환×전환가치÷지출(추정), 목표 미달 판정(`PERFORMANCE_BELOW_TARGET`). 실측 읽기전용 + 미설정 시 추정 입력 하이브리드.
- **성과 전후 비교** — 시뮬 예측 슬롯 vs 실측 병기, 스케일 환산 금지(정직 공개).
- **예산 페이싱** — 월 목표(기본 ₩300만, 중소기업 벤치마크) 대비 실소진·런레이트·여력. 최소예산 ₩1,521은 `campaign_policy.py` 단일원천 → 프론트 자동 반영.
- **자동화 6종** — UTM 자동 부착 · 이상 스캔 주기화 · 빈도 피로 감지(frequency≥3) · 예산 리밸런싱 제안(HITL) · 주간 리포트(LLM 미사용) · 월 목표 계산기.
- **캠페인 이름 AI 제안** — 소재+시뮬 신호로 후보 3개(gpt-4o-mini, 실패 시 결정론 폴백).

### ⑧ 프론트
캠페인 목록/상세/생성 폼, 홈 대시보드(`/manage`, StatCard·ArcGauge·SpendDonut·CampaignRadar·ConversionFunnel), 모니터링(HealthList·KPI·기간 토글), 성과 비교(before-after), 알림 벨/패널(SSE 구독, 401 시 재연결 중단), 챗 옵션 버튼 위젯, 지표 오해 방지 툴팁(도달·CVR·CPM), 렌더 최적화(디바운스·memo).

## 6. 핵심 함수 지도

| 함수 | 위치 | 왜 중요한가 |
|---|---|---|
| `diagnose_campaign` | `detection/agentic_scan.py` | 진단 단일 진실원 — 화면·워커·수동점검이 같은 판단 |
| `run_scan` | `scheduler.py` | 워커 스캔 1사이클(통지+기록+reconcile) |

| `consult_notification` | `remediation/consult_service.py` | 알림→채팅 전이표, CAS 이중심기 방지 |
| `decide_with_confidence` | `agents/regeneration.py` | 진단→처방 + 저확신 시 증액 보류 |
| `judge_tier` / `validate_proposal` | `approval.py` | 승인의 뇌 — Tier 정책표 + 3단계 검증 |
| `Executor.execute` + `build_idempotency_key` | `execution/executor.py` | 지출 단일 경로, 4게이트 + 멱등 |
| CLIO 그래프 + `_grade_kb` | `assistant/graph.py` | ReAct + CRAG-lite, interrupt HITL |
| `build_reader/writer/executor` | `wiring.py` | mock↔실연동 전환 유일 지점 |
