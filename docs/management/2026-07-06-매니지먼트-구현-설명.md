## 1. 큰 흐름 — "관측 → 진단 → 상담 → 제안 → 승인 → 실행 → 기록"의 운영 루프

한 문장으로 하면 **"광고 계정을 계속 관찰하다가 이상하면 알려주고, 대화로 상담해서 처방을 만들되, 돈이 움직이는 일은 반드시 승인을 거쳐 단 하나의 실행 경로로만 나가는 자율운영 루프"** 다.

```
                    ┌────────────── APScheduler 워커 3잡 (이상스캔·주간리포트·리밸런싱) ─────────┐
                    ↓                                                                          │
[관측] Meta reader / mock  ──→  [감지·진단] 결정론 룰 → 애매하면 LLM 재판정 (diagnose_campaign)   │
                    ↓ findings                                                                 │
[알림] PanelSink 판정표 → management_notifications → SSE → 프론트 벨/패널                        │
                    ↓ [상담하기]                                                               │
[상담] 채팅 세션에 상담 카드 심기 → 옵션 버튼 → CLIO(에이전틱 RAG 어시스턴트)                     │
                    ↓ 처방                                                                     │
[제안] 재생성 에이전트 / 캠페인 생성 3갈래 / propose_action  →  ActionProposal                   │
                    ↓                                                                          │
[승인] approval.py — Tier 판정 + 3단계 검증 (Tier 높으면 사람 승인 필수, HITL)                    │
                    ↓ ApprovedAction                                                           │
[실행] Executor — 승인 후 4단계 재검증 + 멱등 실행 + Meta writer (mock/dry_run/live)              │
                    ↓                                                                          │
[기록] 감사 로그 · 멱등키 · automation_runs · 롱텀 메모리(chat_execution_history) ───────────────┘
```

전체를 관통하는 설계 원칙은 두 개다.

- **돈의 단일 경로** — 에이전트든 챗봇이든 라우터든, 지출성 조작은 전부 ActionProposal을 만들 뿐이고 Writer에 닿는 길은 Executor 하나뿐이다.
- **의도적 이중 검증** — 승인 전 3단계(approval)와 승인 후 4단계(executor)는 일부러 중복이다. 승인~실행 사이 시간 갭에 상황이 바뀌는 걸 잡는 defense in depth.

## 2. 세부 트랙

### ① 데이터 게이트 (`adapters/`)

Meta Marketing API를 reader(조회)/writer(집행)로 나눠 포트-어댑터로 감쌌다. org별 OAuth 연결(`meta/oauth.py`, 토큰 AES 암호화 저장)로 조직마다 자기 광고 계정을 붙인다. `mock.py`가 reader 포트를 그대로 구현해서 **API 키 없이도 데모 전체가 재현**되고, mock↔실연동 전환은 `wiring.py` 한 곳에서만 일어난다. writer는 mock/dry_run/validate_only/live 4모드 — use_mock이면 live가 봉인된다.

### ② 감지·진단 (`detection/` + `scheduler.py`)

2단 구조다. 값싼 결정론 룰(게재0·소재피로·지갑소진·예산페이스)이 1차 프리필터를 하고, 성과 미달처럼 애매한 건(INCONCLUSIVE)만 LLM ReAct 에이전트가 Meta 신호를 도구로 조회해 재판정한다. 이 진단이 `diagnose_campaign` 하나로 통일돼 있어 **라우터(화면)·워커(자동 스캔)·수동 점검 버튼이 전부 같은 판단**을 쓴다.

APScheduler 워커 3잡(이상스캔·주간리포트·리밸런싱 제안)은 기본 off, settings로 opt-in이고, 잡 실패가 스케줄러를 죽이지 않게 전부 삼킨다. 정상 게재로 확인된 캠페인은 normals로 내보내 미해결 알림을 자동 해소(reconcile)한다.

### ③ 알림·상담 (`remediation/` + 프론트 벨/패널)

스캐너 findings가 곧장 알림이 되진 않는다. `PanelNotificationSink`가 판정표(무시됨·미열람·쿨다운·dedup)로 스팸을 거르고, 통지가 확정된 건에만 advisor가 LLM 조언을 붙여 저장 + SSE 발행한다. dedup은 모듈 잠금 + DB 부분 유니크 인덱스(org·kind·dedup_key 미해결 1행) 이중 방어.

프론트 벨/패널에서 [상담하기]를 누르면 전이표대로 재검증 후 채팅 세션에 상담 카드를 심는다. 이중 심기는 CAS(조건부 UPDATE)로 막았다 — row lock은 LLM 호출 동안 행을 붙드는 안티패턴이라 채택하지 않음. 카드의 옵션 버튼 클릭은 `option_select`로 챗 요청에 동봉돼 지시문으로 변환된다(tool_hint는 화이트리스트로만 신뢰).

### ④ 처방·제안 (`agents/regeneration.py` + 라우터)

진단→처방 매핑은 결정론 코어(`decide_action`)이고, 저확신이면 돈 늘리는 처방을 보류하는 게이트(`decide_with_confidence`)가 얹혀 있다. 소재가 필요하면 4-3(생성 도메인)에 HTTP로 위임만 하고(매니지먼트는 시안을 만들지도 채점하지도 않음), 금지표현 guard 통과 후 사람이 시안을 고르면 그때 제안을 만든다(AWAITING_SELECTION → package).

캠페인 생성도 3갈래 전부 제안 경유다 — 직접 입력(`create-proposal`), 4-3 시안(`from-candidate`), 4-1 시뮬 결과(`from-simulation`, 클릭의향률·거부율 집행가능 판정 통과 필요).

### ⑤ 승인 (`approval.py`)

action_type별 Tier 정책표(`TIER_POLICY`, 미등록은 보수적으로 Tier 3)로 위험도를 판정하고, 만료·해시 변조·정책 버전 3가지를 검증한다. Tier가 높으면 사람 승인 필수(HITL), 라벨과 판정이 다르면 재라벨 후 감사 대상.

### ⑥ 실행 (`execution/`)

승인 후 4게이트 — ④ ApprovedAction 유효성 재확인(만료·정책버전·hash·tenant·tier) ⑤ `expected_state_version` 낙관적 락 비교(불일치=STALE_PROPOSAL) ⑥ 지출 총액 재계산 + 멱등키 선점 ⑦ 감사 로그(재시도·부분 실패 포함). 멱등키가 `sha256(approval_id + action_type + 대상IDs)`라 같은 승인 건은 몇 번을 눌러도 1번만 집행된다. 타임아웃·레이트리밋 재시도 정책 내장.

### ⑦ 어시스턴트 CLIO (`assistant/`)

LangGraph Tool-calling ReAct. 원칙이 명확하다.

- **수치는 live 도구에서만 인용**(환각 방지) — live_campaigns/live_budget/live_weekly_report 등.
- 해석·정책은 KB 검색(pgvector RAG). 근거가 부족하면 자기교정 검색(CRAG-lite) — LLM이 근거 충분성을 평가하고 쿼리 재작성 후 재검색.
- 최신 정보는 web_search로 보강하되 advisory(참고)로만 인용.
- 운영 변경은 `propose_action`으로 제안만 하고, 승인 필요 Tier면 `interrupt`로 그래프를 멈춰 사람에게 제어를 넘긴다.

LangSmith 기반 eval(진단·환각·충실성·검색)이 `evals/`에 같이 붙어 있다.

### ⑧ 기록·학습 (`core/automation` + 메모리)

워커 결과는 3도메인 공용 `automation_runs`(dedup 유니크 인덱스)에 쌓여 프론트가 조회하고, 실행 확정 건은 `chat_execution_history`(롱텀 메모리)에 남아 어시스턴트가 과거 조치를 회상한다. 주간 리포트·리밸런싱 제안도 여기 적재 — 리밸런싱은 제안만 만들고 실행(예산 이동)은 사람 승인(budget-commit)을 그대로 거친다.

### ⑨ 프론트

캠페인 목록/상세/생성 폼, 모니터링(HealthList·KPI), 성과 비교(before-after), 알림 벨/패널(SSE 구독, 401 시 재연결 중단), 챗 옵션 버튼 위젯, 렌더 최적화(입력 디바운스·자식 memo).

## 3. 중요한 함수

| 함수 | 위치 | 왜 중요한가 |
|---|---|---|
| `diagnose_campaign` | `detection/agentic_scan.py` | 진단 단일 진실원 — 화면·워커·수동점검이 같은 판단 |
| `run_scan` / `_agent_scanner` | `scheduler.py` | 워커 스캔 1사이클(통지 + 기록 + reconcile) |
| `PanelNotificationSink.deliver` | `remediation/panel_sink.py` | 알림 스팸 방지 판정표 |
| `consult_notification` | `remediation/consult_service.py` | 알림→채팅 전이표, CAS 이중심기 방지 |
| `decide_with_confidence` | `agents/regeneration.py` | 진단→처방 + 저확신 시 증액 보류 게이트 |
| `judge_tier` / `validate_proposal` | `approval.py` | 승인의 뇌 — Tier 정책표 + 3단계 검증 |
| `Executor.execute` + `build_idempotency_key` | `execution/executor.py` | 지출 단일 경로, 4게이트 + 멱등 |
| CLIO 그래프 + `_grade_kb` | `assistant/graph.py` | ReAct + CRAG-lite 자기교정, interrupt HITL |
| `build_reader` / `build_writer` / `build_executor` | `wiring.py` | mock↔실연동 전환 유일 지점 |

## 4. 발표 순서 추천

**알림 벨 데모(눈에 보임) → CLIO 상담 데모(대화로 처방) → "그런데 돈은 함부로 안 나간다"(승인 + Executor 안전장치) → 자동화 워커(사람 없을 때도 돈다)** 순이 자연스럽다. 데모 2개로 흥미 → 안전장치로 신뢰 → 자동화로 완성도, 3단 구성.
