# 팀 공유 — 채팅 입구를 오케스트레이터에 연결했습니다 (1차)

작성 2026-06-26 · generator(token-opt 브랜치) · 상세 설계: `docs/superpowers/specs/2026-06-26-unified-chat-assistant-design.md`

## 한 줄 요약

라이브 채팅(`api/routers/chat.py`)이 그동안 안 쓰던 **오케스트레이터(`api/assistant/`)** 를 거치도록 연결했습니다. 이제 채팅이 "광고 만들어줘" 같은 **생성 요청을 생성 서브에이전트로 라우팅**합니다. 관리·CLIO는 그대로입니다.

## 왜 했나 (문제)

채팅 입구가 **두 갈래로 따로 놀고** 있었습니다.

- **라이브 입구** `chat.py /complete` — 관리 키워드면 관리 에이전트, 아니면 CLIO(Gemini). **생성·시뮬은 못 함.** 주석에도 "임시 연결"이라 적혀 있었음.
- **이미 잘 만든 오케스트레이터** `api/assistant/` — 의도분류 → 서브에이전트 디스패치 구조에 생성·관리가 등록돼 있는데, **라이브가 이걸 호출하지 않았음.**

즉 좋은 부품을 만들어두고 안 끼우고 있었습니다. 이번에 그걸 끼웠습니다.

## 무엇을 했나 (이번 변경)

`api/routers/chat.py` 한 곳 + 테스트만 건드렸습니다. 공통 계약·타 도메인 무변경.

```
사용자 메시지
  ├─ 관리 키워드?  → 기존 관리 경로 (그대로, 무변경)
  └─ 그 외        → Orchestrator.run_turn
                      ├─ GENERATE → 생성 서브에이전트(슬롯필링)
                      ├─ (결과 None = advise) → CLIO 폴백(그대로)
                      └─ 결과를 SSE로 변환해 스트리밍
```

- 새 순수 함수 `_subagent_sse_events(result)` — 서브에이전트 결과를 SSE 이벤트로 변환.
  - **ANSWER**(즉답) → meta + 토큰 스트리밍
  - **ASK**(되묻기) → 질문 토큰 스트리밍
  - **TRIGGER**(작업시작) → `started`(stream_url) 이벤트 방출 → 프론트가 잡 진행 구독
- 단위 테스트 3종(`tests/assistant/test_chat_router.py`).

## 왜 이렇게 설계했나 (핵심 결정 + 이유)

팀원이 가장 궁금할 "왜"입니다.

1. **왜 오케스트레이터를 쓰나** — 이미 만들어진 의도분류·디스패치·중립 계약(`core/assistant_contracts.py`)이 있었음. 바닥부터 안 만들고 **연결**만 하면 생성·시뮬·관리를 한 입구로 모을 수 있음.
2. **왜 관리는 안 건드렸나** — 라이브 관리 경로는 이미 멀티턴(`thread_id`)·기록(`record_turn`)·HITL 승인을 갖춰 잘 돈다. 오케스트레이터의 관리 핸들러는 그게 빠진 단순판이라, 무리하게 갈아끼우면 **관리가 멀티턴·로깅을 잃는 회귀**가 난다. 그래서 **"관리는 지금 길 그대로"** — 회귀 위험 0, 관리 팀 의존 0, generator 혼자 완성 가능.
3. **왜 액션 3종(ASK/TRIGGER/ANSWER)인가** — 채팅을 "말만 하는" 게 아니라 **행동하게** 하려고. 정보 부족하면 되묻고(ASK), 오래 걸리는 일은 잡을 시작하고(TRIGGER), 바로 답할 수 있으면 즉답(ANSWER). "에이전트를 넘어 AI 비서" 지향의 토대.
4. **왜 내 부분만 하고 나머지는 기록만 했나** — 6명이 같이 만드는 기능이라, 남의 도메인을 건드리면 머지 충돌이 난다. 그래서 **골격 + 생성 흐름만 구현**하고, 시뮬·관리는 "끼우는 법"만 문서화(관리 팀이 했던 import-ready 방식).

## 팀원이 알아야 할 것 (영향 + 핸드오프)

- **지금 바로 바뀐 것** — 채팅에서 "광고 만들어줘"가 생성 슬롯필링으로 라우팅됨. 관리·일반질문(CLIO)은 동작 그대로.
- **시뮬 팀** — `domain/simulation`에 `build_simulation_chat_agent`(이미지 없으면 ASK, 있으면 시뮬 start → TRIGGER) 구현 → `wiring`에 `Intent.SIMULATE` 한 줄 등록 → `intent.py`에 시뮬 키워드 추가. 시뮬 API(`POST /api/simulation`)가 광고 이미지·`/stream`을 이미 지원하므로 패턴 동일. (설계 §5.1)
- **관리 팀** — 지금은 그대로 둬도 됩니다. 나중에 오케스트레이터로 합치고 싶으면 관리 핸들러에 `thread_id`·`record_turn` 보강 후 `chat.py`의 관리 선분기 제거. (설계 §5.2)
- **공통 계약 변경 예정(공지)** — 채팅 이미지 첨부를 위해 `SubagentRequest`에 이미지 필드 추가 예정. 모두 쓰는 부분이라 바꾸기 전 공지하겠습니다. (설계 §5.3)
- **프론트** — `started`(stream_url) 이벤트를 받아 잡 진행을 구독하는 작업 필요. 시뮬 결과 후 "개선할까요?" 자동 노출도 프론트. (설계 §5.4)

## 검증 상태 (솔직하게)

- ✅ assistant 테스트 9개(기존 6 + 새 3), ruff 통과.
- ⚠️ 자동 테스트는 **"결과→SSE 변환"과 라우팅(스텁)** 까지 검증. "광고 만들어줘 → 실제 생성 잡"의 끝단 통합(실 LLM 경로)은 키·네트워크가 필요해 단위테스트 제외 → **앱 띄워 수동 확인 예정.**
- ⚠️ 프론트 미연결이라 아직 "작업시작" 후 진행상황이 화면에 안 뜸(다음 슬라이스).
