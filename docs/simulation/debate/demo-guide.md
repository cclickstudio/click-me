# 페르소나 토론 — 시연 설명 가이드

> 광고를 집행하기 전에, AI 가상 소비자들이 **토론**으로 광고를 평가하고 개선 방향까지 내놓는 기능.
> 이 문서 하나만 위에서 아래로 따라가면 전체 그림이 잡히도록 정리했다.

---

## 1. 한 줄 소개

숫자(거부율 96%)만 보면 "망했다"는 알지만 **왜 망했는지, 어떻게 고칠지**는 모른다.
이 기능은 서로 다른 AI 모델이 연기하는 **가상 소비자 4명 + 전문가 4명이 토론**해서, 거부 이유를 실제 발언으로 드러내고 개선안까지 만든다.

> 핵심 한 줄 — **"같은 클릭 0%라도, 토론은 *왜* 안 먹혔는지를 소비자 목소리로 설명한다. 돈 쓰기 전에."**

---

## 2. 전체 흐름 (0 ~ 11)

```
0  프로젝트 생성
1  광고 데이터 입력
2  광고 해석(파싱)
3  인구 분포 고정
4  연령·성격·트렌드 입력
5  페르소나 생성
6  타겟 설정
7  반응 출력          ← 가상 소비자들이 광고에 반응 (※ 더미 데이터가 여기)
─────────────────── 여기부터가 이번에 만든 부분 ───────────────────
8  반응 분석          어디서·왜 새는가 (구조 분석)
9  KPI 확정 + 토론 주제   숫자 확정 + "뭘 토론할지" 정함
10 페르소나 토론         전문가 4명 + 소비자 4명 + 진행자(Judge)가 토론
11 리포트 생성          숫자 + 토론 결론 + 실제 발언을 한 장으로
```

> 7번까지는 기존 시뮬레이터가 만든다. **우리가 만든 건 8 ~ 11.**

---

## 3. 핵심 원칙 — "숫자는 기계, 해석은 AI"

| 단계 | 방식 | 이유 |
| --- | --- | --- |
| 8·9·10선발·10배정·11 | **결정론**(규칙·계산, AI 안 씀) | 같은 데이터 → 항상 같은 결과, 빠르고 무료, 재현 가능 |
| 10 토론 발언 | **LLM**(실제 AI 모델) | 사람 같은 의견·대화는 AI만 가능 |

> 숫자를 AI가 지어내면 시뮬레이션이 무의미해진다. **그래서 숫자는 코드로 못박고, AI는 토론(해석)에서만 쓴다.**

## 4. 조각별 설명 (시연 때 이 순서로)

### 조각 8 — 반응 분석 (`tools/debate/analyzer.py`)
반응 데이터를 **구조적으로 해부**한다. 단순 평균이 아니라 "어디서·왜 새는가, 누가 어떤 무리인가".
- AISAS 퍼널 — 주목→흥미→검색→행동→공유 중 **어디서 제일 많이 빠졌나(병목)**
- 이탈·거부·감정 분해 — 왜 떠났나
- 소비자 그룹 — 완주자 / 미온층 / 거부자 / 불신자 / 초기이탈로 분류 (→ 일반인 4명(피벗·완주자·비판자·미온) 선발 풀)

### 조각 9 — KPI 확정 + 토론 주제 (`tools/debate/kpi.py`)
8이 *해부*한 걸 **숫자로 못박고, 토론 안건을 출제**한다.
- 4대 KPI 확정 — 클릭 의향률·구매의도·신뢰도·거부율
- 토론 주제 자동 생성 — 예: 거부율 높으면 "무엇이 거부를 부르나?", 신뢰 높은데 클릭 낮으면 "무엇이 행동을 막나?"

> 8 = 무엇이 문제인가 / **9 = 그걸 숫자로 + 토론이 풀 질문 정의** / 10 = 그 질문으로 토론.
> 9가 없으면 토론이 "무슨 주제로 할지"를 모른다. **8과 10을 잇는 다리.**

### 조각 10 — 페르소나 토론 (`tools/debate/selector.py`·`assigner.py`·`runner.py`)
세 부분으로 나뉜다.
- **구성** — 패널 = **도메인 전문가 2 + 마케팅 전문가 2 + 일반인 N**(`lay_count` 2 또는 4, 기본 4). 일반인(2명=피벗·비판자 / 4명=+완주자·미온)만 실제 반응자에서 뽑고, 전문가 4명은 광고 카테고리에 맞춰 합성한다 (칸쵸 광고면 과자 전문가). **둘 다 돌려보고 좋은 쪽 채택.**
- **배정** — 8명에 AI 모델을 골고루 배정 (Haiku 4 / GPT 4, Gemini 제거), 진행자는 Sonnet. 이름·프로필도 부여.
- **토론** — 라운드마다 역할이 다르다. R1 발산 → R2 반박 → R3 검증. 진행자(Judge)가 정리하고 최종 결론.
  - **2~4라운드 유동** — 의견이 정착하면 일찍 끝내고, 계속 갈리면 한 라운드 더 (숫자로 판단).

> 왜 전문가를 넣나 — 숫자(8·9)는 "어디서 샜나"는 알려줘도 "왜·어떻게 고칠까"엔 전문 지식이 필요하다. **일반인은 자기 실제 반응으로, 전문가는 분석 결과로** 토론한다.
> 왜 모델을 섞나 — "전문가는 GPT, 일반인은 Haiku" 식으로 몰면 의견이 역할 때문인지 모델 말투 때문인지 구분이 안 된다. 그래서 **역할과 모델을 일부러 교차** 배정한다 (Haiku·GPT 두 모델, Gemini는 응답 실패 잦아 제외).

### 조각 11 — 리포트 (`tools/debate/report.py`)
**[KPI 숫자] + [분석] + [토론 결론·실제 발언 인용]** 을 한 장으로 조립한다. 새로 지어내지 않고 앞 결과를 모으기만 한다.

---

## 5. 토론은 이렇게 흐른다

```
진행자(Judge)  토론 주제 제시
   │
R1 발산   8명이 서로 안 보고 독립적으로 반응
   │  → Judge 중간 정리
R2 반박   앞 의견에 동의/반박 (재진술 금지)
   │  → Judge: 멈출까? (의견 정착했나 숫자로 판단)
R3 검증   "이 개선안이면 클릭하겠나?" 검증   ← 필요할 때만
   │
Judge  최종 결론 — 합의점 / 이견 / 개선안 순위
```

## 6. API (4개)

| 엔드포인트 | 하는 일 |
| --- | --- |
| `POST /api/debate/analyze` | 조각 8·9만 — 분석값·KPI·주제를 **즉시** 반환 (토론 전 미리보기) |
| `POST /api/debate/start` | 토론 시작 → `run_id` 반환 (`?use_llm=true` 실제 AI / `?lay_count=2`\|`4` 일반인 수, 기본 4) |
| `GET /api/debate/{run_id}/stream` | 토론 과정을 **실시간**으로 흘려줌 (SSE) |
| `GET /api/debate/{run_id}/result` | 완료된 전체 결과 (분석·KPI·패널·토론·리포트) |

> 입력은 전부 JSON (7번 반응 출력을 그대로 붙여넣기).

---

## 7. 시연 방법

1. 서버 실행 — `cd backend && uv run dev.py`
2. 브라우저에서 Swagger 열기 — `http://localhost:8000/docs`
3. **분석 먼저** — `POST /api/debate/analyze` 에 반응 JSON 붙여넣기 → 거부율·병목·이탈 사유가 바로 나옴 (무엇이 문제인지)
4. **토론** — `POST /api/debate/start?use_llm=true` → `run_id` 복사
5. **실시간 과정** — 브라우저 주소창에 `http://localhost:8000/api/debate/{run_id}/stream`
   → 발언이 하나씩 올라옴 (누가·어떤 입장·왜)
6. **최종 결과** — Swagger `GET /api/debate/{run_id}/result`

> 실제 AI 토론은 30초~1분 걸린다(발언을 또박또박 생성). 빠른 흐름 확인은 `use_llm` 빼면 mock으로 즉시 끝난다.

## 8. 결과 예시 (실제로 돌린 것)

| | 과자 '이름 찾기' 광고 | AI 세탁기 광고 |
| --- | --- | --- |
| 거부율 | 96.4% (강한 거부) | 61.1% (거부 + 무관심) |
| 진단 | 제품 가치 없이 억지 놀이 컨셉 → "나와 무관" | 편익 입증 안 됨 → "내 세탁기 멀쩡한데 왜?" |

> 둘 다 클릭 0%지만 **원인이 다르다.** 과자는 컨셉을 바꿔야 하고, 세탁기는 편익만 증명하면 된다.
> 이게 "숫자만으론 못 보는, 토론이 잡아낸 차이" — 이 기능의 핵심 가치다.

---

## 9. 저장 구조 (참고)

토론 결과는 3개 테이블에 저장한다 (`simulations` 1:N).
- `persona_debates` — 토론 세션 (주제·라운드 수·최종 결론)
- `persona_debate_participants` — 패널 8명 (이름·역할·모델)
- `persona_debate_utterances` — **발언 한 건 = 한 행** (라운드·입장·발언·이유)

> Judge 결론만 저장하면 근거가 사라지므로, **실제 발언을 다 저장**해서 리포트가 "진짜 소비자 목소리"를 인용한다.
> (코드는 완성, 실제 DB 적용은 운영 연결 단계에서.)
