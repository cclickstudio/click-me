# 페르소나 반응 LLM — 로컬 모델 자체 호스팅·파인튜닝 검토 (80GB GPU 확보 시)

> 반응 생성(4-b) 비용을 로컬 오픈 모델로 푸는 안의 검토 메모. 80GB VRAM 확보를 계기로 [PERSONA_LLM_COST_STRATEGY.md](./PERSONA_LLM_COST_STRATEGY.md) §4 (c) 블로커("GPU 없음")를 재검토한다.
> 결론: **80GB는 "GPU 없음" 블로커만 깬다. 핵심 병목은 컴퓨트가 아니라 ① Persona Collapse(동질화) ② 파인튜닝용 라벨 데이터다. 그래서 "학습부터"가 아니라 "30B off-the-shelf + vLLM guided decoding부터" 가고, 기존 분산 게이트로 합격 시 파인튜닝을 건너뛴다. 서빙은 자체 vLLM(HF 매니지드 엔드포인트 아님), 로컬화는 반응 단계에만. 7/8 마감 경로엔 넣지 않고 발표 직전/후 A/B 파일럿.** (작성일: 2026-06-19)

---

## 0. TL;DR

1. **문서에 이미 있다.** `PERSONA_LLM_COST_STRATEGY.md` §3~4가 소형/로컬 모델 + 파인튜닝을 검토했고 결론은 "Phase 2(발표 후)". 미룬 실질 이유 중 하나가 (c) "단일 EC2에 GPU 없음".
2. **80GB가 깨는 건 (c) 하나뿐.** GPU 인프라 블로커는 사라지지만, 동질화·데이터라는 진짜 변수는 그대로다.
3. **계획을 세 갈래로 분리하라** — "학습(파인튜닝)" · "허깅페이스에 올려" · "그 API로"는 별개 결정이고 함정이 다르다.
4. **학습부터 가지 마라.** 80GB면 30B급을 띄울 수 있고, 30B는 off-the-shelf로도 통과할 수 있다. 파인튜닝은 escalation으로 둔다(데이터 병목 회피).
5. **반응만 로컬.** VLM 광고해석·토론은 API 유지(작업별 모델 분리, 문서 §4와 일치).

## 2. 80GB가 바꾸는 것 / 바꾸지 못하는 것

| | 80GB 이전(문서 전제) | 80GB 이후 |
|---|---|---|
| GPU 인프라 | 없음 → 로컬 불가 | **30B급 fp16/8-bit vLLM 서빙 가능** ✅ |
| 워크로드 적합성 | — | 반응 = 독립·짧은 JSON·지연허용 → **vLLM continuous batching에 이상적** ✅ |
| Persona Collapse | 최대 리스크 | **그대로** — 모델 크기로 자동 해결 안 됨 |
| 파인튜닝 데이터 | 미해결 | **그대로** — 컴퓨트가 아니라 데이터가 병목 |
| 구조화 출력 준수 | 소형일수록 위반 | **guided decoding으로 해결 가능**(아래 §3) |

**한 줄**: 80GB는 "띄울 수 있나"를 풀지만 "다양성을 지키나 / 무슨 데이터로 학습하나"는 안 푼다.

## 3. 계획을 세 갈래로 분리하라

### A. "학습(파인튜닝)"을 출발점으로 두지 마라 — 80GB면 건너뛸 수도 있다

문서가 파인튜닝을 요구한 건 **1~8B 초소형** 기준이다. 80GB로는 **30B급**(EXAONE 30B·HyperCLOVA SEED 32B)을 띄울 수 있고, 30B는 off-the-shelf로도 동질화·한국어·구조화를 통과할 여지가 있다. 순서는,

1. **파인튜닝 없이** 30B + `temperature=1.0` + **vLLM guided JSON decoding**(outlines/xgrammar류 — §3.5 스키마를 100% 강제. 문서 §3.4-③ "구조화 출력 준수" 리스크가 학습 없이 공짜로 해결).
2. 기존 `variance_warning`/`effective_n` + **KOBACO 구매의도 분포**로 합격/불합격 게이트 측정.
3. **떨어질 때만** 파인튜닝으로 escalate.

→ 30B가 통과하면 파인튜닝의 진짜 병목(B)을 통째로 피한다.

### B. 파인튜닝의 숨은 병목은 GPU가 아니라 "학습 데이터"다

문서가 "투자지 지름길 아님"이라 한 부분을 날카롭게 보면 — **무슨 데이터로 학습하나?**

- **Gemini 출력 증류(distill)** → 품질은 Gemini에 캡되고, **증류는 학생을 교사 모드로 수렴시켜 다양성을 오히려 죽인다.** 지키려던 바로 그 다양성을. Polypersona 이득은 *분산을 보존하는 persona-grounded 데이터*에서 나오지 generic 증류에서 안 나온다.
- **실제 설문 응답 학습** → 커버리지 없음. 구매의도는 KOBACO 검증 대상이라 분포가 바뀌면 재검증 부담.

→ 파인튜닝은 컴퓨트 문제가 아니라 **라벨된 페르소나-반응 데이터 소싱 문제**다. 이걸 풀기 전엔 80GB가 있어도 착수 못 한다.

### C. "허깅페이스에 올려 API로"는 두 가지를 섞고 있다

- HF **Inference Endpoints(매니지드)** = 당신이 GPU를 **빌리는 유료 호스팅** + scale-to-zero **콜드스타트**. 300~1,000개 버스트에 안 맞는다. 80GB를 **소유**했다면 거기에 **vLLM 직접 서빙(OpenAI 호환 엔드포인트 노출)**이 맞다 — 내 GPU 값을 HF에 다시 낼 이유가 없다.
- HF **Hub**(가중치 저장·버전관리)는 좋다(파인튜닝 산출물 올려두기). 하지만 **서빙은 자체 vLLM.** "올려서 API"의 두 의미를 분리한다.

## 3.5 모델·제공자 옵션 비교 — Gemma·DeepSeek·Groq·GLM (2026-06 검색 기준)

후보로 자주 언급되는 옵션들을 같은 잣대로 본다. **셋이 같은 층위가 아님**부터 분리 — Gemma는 모델, DeepSeek은 모델+API, Groq는 추론 제공자(API), GLM은 모델(+Z.ai API). 축은 둘 — **모델 축**(한국어 utterance가 구속 조건) × **서빙 축**(소유 80GB 자체 vLLM=한계비용≈전기료 / 매니지드 API=토큰 과금).

### ⚠️ 벤치마크 적합성 갭 (먼저 박아둔다)

"GPT-5.2를 이겼다 / Opus의 94.6%" 류 헤드라인은 전부 **SWE-bench·AIME·LiveCodeBench = 코딩·수학·에이전트 추론** 점수다. 우리 구속 조건은 ① **한국어 `utterance` 품질** ② **다양성 보존(Persona Collapse)** ③ **대량 저비용 JSON**이고, **이 셋을 그 리더보드는 안 잰다.** 코딩 1위가 자연스러운 한국어 한 문장을 잘 쓰거나 페르소나 분산을 지킨다는 보장은 없다. → **벤치 점수로 모델을 고르지 말 것.**

### 옵션별 평가

| 옵션 | 정체 | 80GB 자체호스팅 | 한국어 utterance | 발목 |
|---|---|---|---|---|
| **Gemma 3 27B** | 구글 오픈 모델 | ✅ 여유 | ⚠️ 2순위(문서 §3.3) | 같은 30B면 한국어 네이티브가 우위 |
| **DeepSeek V3/R1** | 중국 오픈 + 초저가 API | ❌ 671B 안 들어감 | △ | API=중국 호스팅(데이터 거주성) |
| **DeepSeek R1-Distill 32B** | 위 증류본 | ✅ fit | △ | **reasoning 모델 — 과함**(CoT 출력 낭비) |
| **Groq** | LPU 추론 API | — (남의 인프라) | 카탈로그 의존 | 토큰 과금 재발·한국어 네이티브 부재·TPM 한도 |
| **GLM-4.5 / 4.6** | Zhipu 오픈 MoE 355B(32B active) | ❌ 불가 / Air 106B만 빠듯 | ⚠️ 2순위(중국어 네이티브) | 강한 변형은 80GB 초과 |
| **GLM-5** (2026-02) | 744B MoE(40B active), SWE-bench 77.8% | ❌ 불가(4bit ~370GB) | ⚠️ 2순위 | 코딩·추론 벤치만 강함 |
| **GLM-5.1** (2026-03) | 증분, 코딩 Opus 4.6의 ~94.6% | ❌ | ⚠️ | 위와 동일 |
| **GLM-5.2** (2026-06) | 1M ctx, **MIT**, API ~10배 저렴 | ❌(744B급) | ⚠️ | 출시 직후 성숙도 미검증 |

### 판단 — DeepSeek·GLM은 같은 바구니

- **강한 GLM(4.6·5·5.2)·DeepSeek(V3/R1)은 전부 80GB에 안 들어간다.** 자체호스팅 후보는 GLM-4.5-Air(106B, 빠듯)·DeepSeek-Distill-32B(reasoning, 과함) 정도이고 둘 다 약하거나 부적합. → **소유 80GB의 비용 이점을 못 살린다.**
- **API 경로는 전부 중국 호스팅**(Z.ai/Zhipu·DeepSeek) → 광고 크리에이티브·예산 데이터 **거주성/거버넌스 플래그**(CLAUDE.md 기밀 데이터 원칙). 조용히 도입할 항목이 아니라 명시적 결정 사항.
- **Gemma**는 자체호스팅 되지만 한국어가 약점 → 같은 30B면 EXAONE/HyperCLOVA가 우위.
- **Groq**는 소유 GPU 전제와 충돌(토큰 과금 재발)하고 카탈로그에 한국어 네이티브가 없다. **유일한 자리 = 온라인 미리보기(≤50명, 속도)** 하이브리드.
- **GLM-5.2의 MIT + 초저가 API**만, "데이터 거주성 OK + 한국어 게이트 통과" 조건부로 **"싼 API" 칸(Flash-Lite·DeepSeek API와 동급)**에 추가될 수 있다. 단 소유 80GB 이점과는 무관.

→ **결론 불변** — 구속 조건이 코딩 점수가 아니라 한국어·다양성·소유 GPU 활용이므로, 중심은 **한국어 네이티브 30B 자체 vLLM**. Gemma·DeepSeek·Groq·GLM은 "벤치는 좋아도 한국어 2순위 + 거주성/크기 발목"이라는 같은 변형이다.

> 출처(2026-06 검색): GLM-5 744B/SWE-bench 77.8%·GLM-5.1·GLM-5.2(MIT·~10배 저렴) buildfastwithai·serenitiesai·aiforanything; GLM-4.5 355B(32B active)·Air 106B arXiv 2508.06471·DeepLearning.AI The Batch; GLM-4.6 IntuitionLabs.

## 4. 전부 로컬화하지 마라 — 반응만

비용의 ~99%인 **반응(N콜)만** 로컬로 내리고, 나머지는 API 유지(작업별 모델 분리 = 문서 §4).

| 단계 | 콜 수/런 | 특성 | 권고 |
|---|---|---|---|
| `interpret_ad` (VLM) | 1 | 멀티모달 비전·레버리지 큼 | **Gemini 유지** — 80GB 로컬 VLM은 비전 약함 |
| **반응 (4-b)** | **N (300~1,000)** | 독립·짧은 JSON·지연허용 | **로컬 vLLM 후보** — 양 많고 단순 |
| 토론 (9콜) | 9 | 추론·Haiku/GPT/Sonnet 의도적 조합 | **API 유지** |

→ 로컬은 **양 많고 단순한 곳**에서만 값을 한다.

---

## 5. 비용은 0이 되지 않는다 — opex·운영으로 전환될 뿐

로컬은 토큰 과금을 **GPU opex + 운영/엔지니어링 시간**으로 바꾼다.

| 조건 | 한계비용 | 판단 |
|---|---|---|
| **소유 하드웨어**(매몰비용) + 대량 | ≈ 전기료 | **API를 이긴다** |
| **클라우드 렌탈**(A100 80GB ~시간 $1.5~2) + 저볼륨 | 시간당 고정비 | **API(Flash-Lite+배치)가 여전히 쌈** |

→ 손익분기는 "소유 vs 렌탈 × 런 볼륨"의 함수다. 출시 전 낮은 볼륨에선 API가 보통 더 싸고 운영도 가볍다.

## 6. 권고 (종합)

### 7/8 마감 경로 — 로컬 넣지 않는다
- API 레버로 간다 — **표본 N 적정화(300) + 프롬프트 프리픽스 캐싱 + 반응만 Flash-Lite급**. (리스크 최소, [PERSONA_LLM_COST_STRATEGY.md](./PERSONA_LLM_COST_STRATEGY.md) §4 / [BATCH_API_STRATEGY.md](./BATCH_API_STRATEGY.md))

### 발표 직전/후 — 로컬 A/B 파일럿
1. **파인튜닝부터가 아니라** 30B off-the-shelf(EXAONE 30B / HyperCLOVA SEED 32B) + **vLLM guided decoding**부터.
2. 기존 `variance_warning`/`effective_n` + **KOBACO 구매의도 분포 재현**을 합격 게이트로 A/B 측정.
3. **통과 → 파인튜닝 불필요**(데이터 문제 회피). **불통과 → 데이터 소싱 + persona-grounded 파인튜닝** 착수.
4. 서빙은 **자체 vLLM**, HF는 **가중치 저장만**. 로컬화는 **반응 단계에만**.

### 의사결정 전 확인 필요
- **80GB는 소유인가 렌탈인가** — §5 손익분기가 여기서 갈림.
- **예상 런 볼륨**(하루/주 횟수 × 회당 N) — 낮으면 로컬은 과투자.
- **파인튜닝용 데이터 계획** — 없으면 30B off-the-shelf 경로로 못 박는다.

---

## 7. 한 문장 요약

**80GB는 문서가 미룬 "GPU 없음" 블로커만 깬다. 진짜 변수는 동질화와 파인튜닝 데이터라서, 학습부터가 아니라 30B off-the-shelf + vLLM guided decoding으로 시작해 기존 분산 게이트로 통과하면 파인튜닝을 건너뛰고, 서빙은 자체 vLLM으로 반응 단계만 로컬화하며, 마감 경로엔 API를 유지한다.**
