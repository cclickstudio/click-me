# 반응 분석 → 페르소나 토론 파이프라인 설계

> 더미데이터(`backend/domain/simulation/dummy/reaction-dummy.json`)를 분석하고,
> 그 결과로 페르소나 토론을 돌려 광고 개선 리포트를 만드는 전체 설계.

## 한눈에 보는 흐름

```
반응 데이터(19명) → ① 결정론적 집계(숫자 확정) → ② 토론 페르소나 6명 선발(규칙)
                  → ③ 모델 배정(자동) → ④ 3라운드 토론(해석) → 리포트
```

**대원칙**: 숫자는 결정론(집계), 해석은 LLM(토론). 둘을 섞지 않는다.
토론은 항상 실제 반응 데이터에 고정(grounded)되어야 한다 — 새로 지어내면 시뮬레이션이 무의미해진다.

---

## 용어 풀이 (먼저 읽기)

전부 **AISAS 퍼널**(주목 → 흥미 → 검색 → 행동 → 공유) 기준입니다.

| 용어 | 쉬운 뜻 | 이 데이터 예시 |
| --- | --- | --- |
| **완주자** | 광고 보고 끝까지(행동/클릭까지) 간 사람 | P-00006 |
| **피벗** | 딱 중간, 조금만 밀면 넘어올 "스윙 보터" 같은 사람 | P-00011 |
| **거부자** | 광고를 대놓고 싫어한 사람 (`rejected`) | P-00000 |
| **불신자** | 광고를 못 믿는 사람 (`distrust`) | P-00013 |
| **초기 이탈** | 시작(흥미 단계)부터 떨어진 사람 | P-00010 |
| **미온 다수** | "관심은 있는데 굳이 클릭/검색은 안 한" 사람들 — 이 광고에서 제일 많았던 무리(절반 가까이) | P-00011·P-00009 등 |
| **신뢰-행동 갭** | 믿음(trust)은 큰데 살 마음(purchase_intent)은 안 따라온 정도 = `trust − purchase_intent` | 피벗 선정 기준(②) |
| **stance(입장) 점수** | 이 사람이 얼마나 긍정/부정인지 1차원으로 매긴 것 (**③ 모델 배정 전용**) | -7.5(거부) ~ +4.5(완주) |

> **"미온 다수"가 핵심.** 이 광고는 사람들이 *싫어한* 게 아니라 *안 움직인* 게 문제다.
> 그래서 "관심은 있는데 클릭 안 한 무리"를 어떻게 움직이게 하느냐가 캠페인의 숙제.

## ① 분석 결과 도출 (집계)

**LLM 안 씀. 결정론적 집계.** KPI는 SSR 기반이라 토론이 숫자를 만들면 안 된다.

이 데이터(19명) 집계 결과:

### AISAS 퍼널 — 어디서 새는가

```
주목 19 (100%) → 흥미 17 (89%) → 검색 5 (26%) → 행동 5 (26%) → 공유 1 (5%)
                                  ↑ 흥미→검색 구간에서 12명 이탈 = 최대 병목
```

### 4대 KPI

| KPI | 값 |
| --- | --- |
| 클릭 의향률 | 26.3% (신뢰구간 10.5~47.4%, 행동 5/19) |
| 구매의도 | 평균 3.0 — 평균 단언 금지, **분포로 표기** |
| 신뢰도 | 평균 4.05 (높음 — 브랜드 인지도) |
| 거부율 | 5.3% (1/19) |

### 한 줄 해석 (토론 시드)

> 신뢰·흥미는 높은데(89%, 4.05) 클릭 전환이 안 된다(26%). 이탈 절반이 "더 알아볼 이유가 없어서".
> **알리는 데는 성공, 움직이게 하는 데는 실패.**

> **캠페인 목표**: 인스타 광고이므로 구매 전환보다 **클릭 유도**가 핵심.
> KPI 가중을 구매의도가 아니라 클릭 의향률·흥미→검색 이탈에 둔다.

## ② 토론 페르소나 6명 선발 (규칙 기반·자동)

**LLM 안 씀. 결정론적 규칙.** 재현성·감사 가능·비용 0. 아키타입은 구조화 필드에 이미 다 들어있다.

> "선발"은 새로 만드는 게 아니라 **실제 반응자 전원 중에서 6명을 고르는 것.**
> 일반인을 새로 생성하면 데이터와 단절되고, 전원 전문가로 바꾸면 소비자 반응과 단절된다.

> **규칙은 절대값을 박지 않는다.** 아래는 전부 "조건 필터 → 정렬 → 타이브레이크"의 *상대적 선택*이라,
> 데이터가 바뀌면 그 데이터 안에서 다시 계산된다. 표의 `P-0000x`는 더미에 돌린 *예시 결과*일 뿐 규칙이 아니다.

### 6개 고정 슬롯 + 우선순위

희소 신호(거부·불신)를 먼저 확보 → 흔한 무리는 나중에. **위에서부터 순서대로 채우되, 이미 뽑힌 사람은 후보에서 뺀다**(한 사람이 여러 슬롯 조건을 동시에 만족할 수 있으므로 — 예: 거부자가 불신·초기이탈도 해당).

```
슬롯1 [완주자]   action == true 인 무리의 '전형'        끝까지 간 사람들의 대표
슬롯2 [피벗]     신뢰-행동 갭이 가장 큰 1명 ★핵심        신뢰는 됐는데 행동만 안 함
슬롯3 [거부자]   rejected == true                      대놓고 싫어한 사람 (희소→필수)
슬롯4 [불신자]   emotion_tag == "distrust"             못 믿는 사람
슬롯5 [초기이탈] drop_stage == "interest"               흥미 단계서 떨어진 사람
슬롯6 [미온 2]   피벗과 신뢰(trust)가 가장 다른 미전환자   같은 미전환 무리의 다른 결
```

### 슬롯2 피벗 — 기준은 stance가 아니라 '캠페인이 푸는 질문'

피벗은 "**조금만 밀면 넘어올 스윙보터**"다. 그런데 `stance_score`(③) 0에 가까운 사람은 "거부 신호와 약한 긍정이
*우연히 상쇄*된" 사람이라 — 안 믿어서 안 움직인 사람도 0이 될 수 있다. 안 믿는 사람은 밀어도 안 넘어온다.

이 캠페인의 질문은 "**신뢰는 높은데 왜 클릭 안 하나**"이므로, 피벗은 **신뢰는 이미 확보됐는데 행동만 안 한** 사람이다.

```python
def is_undecided(p):                      # 미전환: 흥미는 있으나 행동 안 함
    return p.interest and not p.action

def pick_pivot(pool):
    cands = [p for p in pool if is_undecided(p)]
    if not cands:
        return None                       # 엣지케이스 규칙으로 보충
    # ① 신뢰 절대값 최고("신뢰는 높은데") → ② 신뢰-행동 갭 최대 → ③ id 사전순
    tmax = max(p.trust for p in cands)
    top = [p for p in cands if p.trust == tmax]
    gmax = max(p.trust - p.purchase_intent for p in top)
    final = [p for p in top if p.trust - p.purchase_intent == gmax]
    return min(final, key=lambda p: p.persona_id)
```

> **피벗 기준은 캠페인 목표에서 파생된다.** 클릭 전환 캠페인이라 "신뢰-행동 갭"을 쓴다.
> 신뢰 구축이 목표인 캠페인이면 다른 기준(예: 신뢰 낮은데 흥미는 있는 사람)으로 바꾼다.
> `stance_score`는 ③ 모델 배정 전용으로만 쓰고, 피벗 선정엔 쓰지 않는다.

### 슬롯6 미온 2 — 피벗과 결이 다른 두 번째 목소리

가장 큰 미전환 무리는 토론 5명 안에선 피벗 1명밖에 대표 못 한다. 그래서 그 무리에서
**피벗과 신뢰가 가장 다른** 한 명을 더 넣어 비중대로 대표되게 한다(피벗이 "믿는데 안 움직임"이면, 대비되는 "별로 안 믿어서 안 움직임").

```python
def pick_second_undecided(pool, pivot):
    cands = [p for p in pool if is_undecided(p)]
    if not cands:
        return None
    dmax = max(abs(p.trust - pivot.trust) for p in cands)
    top = [p for p in cands if abs(p.trust - pivot.trust) == dmax]
    return pick_representative(top)       # 동점은 전형(중앙값 근접)→id순
```

### 타이브레이크 (같은 슬롯에 후보 여러 명)

그룹의 **중앙값에 가장 가까운 1명** = "가장 특이한 사람"이 아니라 "가장 전형적인 사람".
모든 슬롯이 같은 패턴 — **조건 필터 → `pick_representative` 타이브레이크**(완주자 포함, 예외 없음).

```python
def pick_representative(group):
    pi_med = median(p.purchase_intent for p in group)
    tr_med = median(p.trust for p in group)
    return min(group, key=lambda p:
        abs(p.purchase_intent - pi_med) + abs(p.trust - tr_med))
    # 동점이면 persona_id 사전순 → 완전 재현성
```

### 엣지 케이스

- **슬롯에 해당자 없음**(예: 좋은 광고라 거부자 0명) → 비우지 말고 다음 우선순위 무리에서 보충.
- **항상 비판자 1명 확보**: 부정이 0명이어도 `min(stance_score)`인 "가장 덜 긍정"인 사람을
  비판 역할로 넣는다 → 칭찬 일색 메아리방 방지. 좋은 광고에선 이 1명이 "천장"을 알려줌.
- 슬롯은 "긍/부정 쿼터"가 아니라 **"분포 범위를 커버"** → 데이터가 긍정으로 기울면 패널도 긍정으로 자동 적응.

### 이 데이터의 선발 결과 (6명) — 규칙을 더미에 돌린 *예시*

| 슬롯 | 선발 | 규칙이 고른 근거 |
| --- | --- | --- |
| 완주자 | P-00006 | `action==true` 5명의 전형(중앙값 근접→id순) |
| 피벗 ★ | P-00011 | 미전환자 중 신뢰 최고(5)·갭 최대(2)·id 최소 → "믿는데 행동 안 함" |
| 거부자 | P-00000 | `rejected==true` (먼저 채워 불신·초기이탈 슬롯에서 제외됨) |
| 불신자 | P-00013 | 거부자 제외 후 남은 `distrust` |
| 초기 이탈 | P-00010 | 거부자 제외 후 남은 `drop_stage=="interest"` |
| 미온 2 | P-00009 | 미전환자 중 피벗(trust 5)과 신뢰 차 최대(trust 3) |

## ③ 페르소나에 AI 모델 배정 (자동)

페르소나 ≠ 모델. **페르소나는 LLM에 넣는 "캐릭터 설정 + 실제 반응 데이터"** 일 뿐이다.
모델 1개로 6명을 다 연기할 수 있다 — system 프롬프트만 다르게 6번 부르면 된다.

### 구성

```
Judge          : Anthropic (Opus 4.8)        — 종합·최종 액션 (추론이 핵심)
토론자 6명      : Haiku 2 + GPT 2 + Gemini 2   — 세 엔진 균등, 소비자 연기엔 저가 라인으로 충분
  └ 피벗        : Haiku 4.5 (고정)             — 가장 중요한 질문, 연기엔 Haiku로 충분
```

> 토론자 6명을 세 엔진에 2명씩 균등 배분. 피벗은 Haiku 2명 중 하나로 고정한다.

> 왜 이렇게? **호출 많은 곳은 싸게, 적고 중요한 곳은 비싸게.**
> 토론자는 6명 × 3라운드 = 많이 부르니 저가, Judge는 3번만 부르니 강모델.
> 의견 다양성의 진짜 원천은 모델이 아니라 각 페르소나가 든 **실제 반응 데이터**다.

### 배정 기준 — 입장 순으로 번갈아 (엔진 ⊥ 입장)

**절대 금지**: "긍정은 GPT, 부정은 Gemini" 식으로 몰기 → 모델 편향과 입장이 뒤섞여
나중에 어떤 의견이 "페르소나라서"인지 "모델 말투라서"인지 구분 불가.

→ 입장(stance) 순으로 정렬한 뒤 엔진을 **번갈아** 배정하면 각 엔진이 긍정·부정을 골고루 갖는다.

```python
JUDGE_ENGINE = "opus"          # Opus 4.8 (별도 고정)
PIVOT_ENGINE = "haiku"         # Haiku 4.5 (피벗에 고정)
# 피벗 제외 5명에게 남은 쿼터: Haiku 1 + GPT 2 + Gemini 2 → 토론자 총 Haiku 2 / GPT 2 / Gemini 2
# 입장 순 정렬 후 이 순서로 채워 한 엔진이 한쪽 입장에 쏠리지 않게 한다.
REST_QUOTA = ["gpt", "gemini", "haiku", "gpt", "gemini"]

def assign(personas, pivot_id):
    rest = sorted((p for p in personas if p.persona_id != pivot_id),
                  key=lambda p: (stance_score(p), p.persona_id))
    out = {pivot_id: PIVOT_ENGINE}
    out.update({p.persona_id: REST_QUOTA[i] for i, p in enumerate(rest)})
    return out   # Judge는 별도 고정

def stance_score(p):
    # AISAS 전 단계 매핑(이를수록 부정) + 미정의 값 방어. drop_stage 는 LLM 출력이라
    # attention·action 같은 값도 올 수 있어 .get 으로 KeyError 를 막는다(미정의=중립 1).
    stage_rank = {"attention": 0, "interest": 0, "search": 1, "action": 2, "share": 2, None: 3}
    s = stage_rank.get(p.drop_stage, 1)
    s += (p.purchase_intent - 3) + (p.trust - 3) * 0.5
    if p.rejected:
        s -= 5
    return s
```

- 토론자 6명 = **Haiku 2(피벗 포함) / GPT 2 / Gemini 2**. 피벗은 Haiku로 고정.
- 전부 결정론 → 같은 데이터면 항상 같은 배정 (재현·감사 가능). 사람 손 안 탐.
- 비율 바꾸려면 `REST_QUOTA` 리스트만 수정.

### 왜 전 과정이 자동인가

입장 점수가 `rejected`·`drop_stage`·`purchase_intent`·`trust` 같은 **이미 있는 필드**에서만 나온다.
선발·피벗 선정·모델 배정 모두 순수 규칙 → **LLM 판단 불필요.** LLM은 이 뒤 토론에서만 쓴다.

## ④ 토론 라운드 (3라운드 고정)

라운드는 고정(비용 예측·재현성·LangGraph 용이). 단 **라운드마다 역할(동사)을 다르게** —
같은 토론을 반복하면 동어반복 + 인위적 수렴만 생긴다.

```
J   토론 주제 제시 (고정 프레임 + 분석결과 초점 주입)
    "신뢰 높은데 클릭 안 됨 — 무엇이 막는가?"
 │
R1 [발산]   병렬·독립    A│B│C│D│E│F  ← 서로 안 보고 주제에만 반응 (순서편향 0, 동시호출로 빠름)
 │
J   중간 정리: 의견 군집화 → 핵심 긴장점 1개로 압축
 │
R2 [반박·수렴] 순차·반응형  A→B→…→F   ← R1 전체 + J 질문 보고 동의/반박 (재진술 금지)
 │
J   ★개선 레버 1~2개를 "잠정 액션"으로 제안
 │
R3 [검증]   순차    A→B→…→F   ← "이 액션이면 당신은 클릭하겠나?" (R2 복사 아님, 새 질문)
 │
J   최종 요약: 합의 + 잔여 이견 + 우선순위 액션
```

### 라운드별 역할

| 라운드 | 동사 | 목적 |
| --- | --- | --- |
| R1 | 발산 | 독립 반응 수집 (오염 없는 의견 분포) |
| R2 | 반박 | 상호작용·수렴 (긴장점 규명) |
| R3 | **검증** | Judge 제안 액션을 소비자 패널에 테스트 (개선안 신뢰도) |

### 핵심 포인트

- **R1은 병렬·독립** — 서로 못 보게 해서 휩쓸림(anchoring) 제거 + 동시 호출로 빠름.
- **R2는 반응형** — "재진술 말고 동의/반박하라" → 고정 구조 안에서 상호작용 발생.
- **R3는 검증** — R2 복사가 아니라 "제안 액션이 먹히나"를 소비자에게 물음.
  거부자(P-00000)가 그 액션에도 안 움직이면 그대로 리포트 신호가 됨.
- **짝수(6명) 걱정 불필요** — 다수결이 아니라 **Judge가 종합·타이브레이크**. 동수 교착 없음.
- **출력 구조화** — 발화를 `{stance, 이유, 제안 레버}` + utterance로 받으면
  Judge가 결정론적으로 집계, 리포트가 그대로 소비.

### LangGraph 매핑

```
topic(J) → [fan-out 병렬: 6명] → reduce(J 중간)
         → [fan-out 반응형: 6명] → reduce(J 액션제안)
         → [fan-out 검증: 6명] → reduce(J 최종)
```

R1·R2·R3 = fan-out(6명), Judge = reduce 노드. 프롬프트는 라운드별 3종 + Judge 3종.

### 유동 라운드 (2~4라운드 자동 조절)

3라운드 고정이 기본이지만, **결론이 일찍 나면 덜 돌고 미심쩍으면 한 라운드 더** 돌리게 자동화한다.
멈춤 판단은 *느낌*이 아니라 *숫자*로 한다 (라운드마다 두 지표를 계산 — 구조화 필드라 결정론).

| 지표 | 뜻 | 계산 |
| --- | --- | --- |
| **churn(변동)** | 지난 라운드 대비 입장 바꾼 사람 수 | `stance` 바뀐 페르소나 수 |
| **dispersion(분산)** | 의견이 얼마나 갈렸나 | 이번 라운드 `stance` 점수의 퍼짐 |

**3갈래 게이트** — "갈렸다 = 무조건 더"가 아니다. 안 바뀌는데 갈려 있으면 더 돌려도 동어반복이라 멈춘다.

```
라운드 N(≥2) 끝
   ├ churn 낮음 + dispersion 낮음  → 정착+합의   → 멈춤 (consensus)   ← 2라운드만에 끝낼 수도
   ├ churn 높음 (아직 움직임)        → 한 라운드 더 (max 안에서)        ← 미심쩍으면 4라운드까지
   └ churn 낮음 + dispersion 높음  → 굳은 이견   → 멈춤 (dissensus)  ← "이견 존재"로 기록
```

```python
MIN_ROUNDS, MAX_ROUNDS = 2, 4   # 최소 2(발산+반박) / 최대 4(비용 상한·종료 보장)
CHURN_TH, DISP_TH = 1, 1.5      # 변동 1명 이하 = 정착 / 분산 1.5 이하 = 합의

def should_continue(round_n, churn, dispersion):
    if round_n < MIN_ROUNDS:
        return True                 # 최소 라운드 전엔 무조건 진행
    if round_n >= MAX_ROUNDS:
        return False                # 상한 도달 → 종료
    if churn <= CHURN_TH:           # 더 이상 안 움직임 → 합의든 이견이든 종료
        return False
    return True                     # 아직 움직임 → 한 라운드 더
```

- LangGraph에선 Judge-reduce 뒤 **조건부 엣지** 하나로 구현 (계속 → fan-out 회귀 / 종료 → 최종 요약).
- 트레이드오프: **재현성이 살짝 떨어진다**(발언이 LLM이라 churn이 매번 다름). 단 min2/max4로 비용·종료는 보장.
- output에 `rounds_run`(실제 라운드 수)·`stop_reason`(consensus/dissensus/max)을 기록해 추적 가능하게 한다.

## ⑤ Output (DB 저장 + 리포트 입력)

토론 단계가 내놓는 최종 결과. **Judge 요약(결론) + 페르소나 발언 전체(증거)** 를 둘 다 담는다.
Judge 요약만 저장하면 근거가 사라지므로, 발언도 같이 저장해 리포트가 "실제 소비자 목소리"를 인용한다.

### 페르소나명 부여 (P-00009 → 사람 이름)

`persona_id`(P-00009)는 DB 내부 번호일 뿐, 리포트엔 못 쓴다. **사람 이름 + 한 줄 프로필**을 붙인다.

- 페르소나는 인구 데이터에서 샘플링되어 성별·나이·성향(OCEAN)을 이미 갖는다 → 그걸로 이름·프로필 생성.
- **결정론적으로**(persona_id 기반) 부여 → 같은 페르소나는 항상 같은 이름. 토론·리포트가 같은 이름 공유.
- 부여 위치는 **페르소나 생성 단계**(`tools/persona/factory.py`)에서. 끝까지 들고 다닌다.
- 예: `P-00009` → `persona_name: "박준호"`, `persona_profile: "29세 직장인 남성 · 미온형"`.

### 리포트(§4)가 소비하는 매핑

| 리포트 항목 | 가져오는 곳 |
| --- | --- |
| 진단 헤드라인 | `judge.final.headline` |
| 개선안 순위 | `judge.final.ranked_actions` |
| "실제 소비자 목소리" 인용 | `participants[].utterances[].text` + `persona_name` |
| 합의/이견 표기 | `judge.final.consensus` / `dissent` |

> 한 줄 정리: **participants = 누가 무슨 말 했나(증거), judge.final = 결론·개선안(해석).**
> 둘 다 저장 → 리포트가 [숫자 KPI + 결론 + 실제 발언 인용]으로 조립된다.
