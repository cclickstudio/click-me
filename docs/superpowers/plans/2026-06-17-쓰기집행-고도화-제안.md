# 쓰기·집행 루프 고도화 제안 (🅱 영역)

작성일: 2026-06-17
대상: 🅱(execution·writer 소유자) / 작성: 🅰(read·analysis)

> 목적: management 도메인에 이미 구현돼 있으나 "봉인"된 쓰기·집행 루프를, 프로젝트 맥락(🅰/🅱 경계·v1 LIVE 봉인·exploratory 원칙)을 깨지 않고 단계적으로 고도화하는 방향과 App Review 권한 영향을 🅱 검토용으로 정리한다. 실제 구현 결정·실행은 🅱 몫이다.

---

## 1. 현황 — 닫힌 루프가 이미 통째로 존재

`detection → diagnosis(LLM) → regeneration → approval(🅰) → executor(🅱) → writer(🅱)` 가 다 짜여 있고, 쓰기 경로만 의도적으로 막혀 있다.

- **Writer** (`adapters/meta/writer.py`) — `pause` · `adjust_budget` · `replace_creative` · `create_campaign`
- **Executor** (`execution/executor.py`) — 멱등키·낙관적 락·재시도·부분실패·감사로그, 지출 단일 경로
- **안전장치** — 예산 하드/소프트캡(`execution/tier.py` 90/95/100%), Tier별 사람 승인, 토큰 로그 마스킹(게이트 #8)

핵심은 실행 모드 봉인(`writer.py` 상단 주석 + `executor.py` `DEFAULT_ALLOWED_MODES`).

| 모드 | 동작 | 상태 |
| --- | --- | --- |
| `DRY_RUN` | 요청 빌드만, 미전송 | 현재 기본값 |
| `VALIDATE_ONLY` | 실제 API 전송 + Meta 검증만, 변경 없음 | v1 허용 상한 |
| `LIVE` | 실제 변경 | 코드는 존재, `DEFAULT_ALLOWED_MODES` 밖이라 봉인 |

LIVE는 `§7 Must`로 v1에서 일부러 막은 상태. 무시하고 LIVE부터 켜면 프로젝트 규칙에 어긋난다.

## 2. 고도화 3단계 (맥락 안에서)

### 1단계 (지금) — VALIDATE_ONLY로 루프를 실 API로 가동

`management_execution_mode`를 `DRY_RUN → VALIDATE_ONLY`로 올리면, 진짜 Graph API를 호출하되 `execution_options=['validate_only']`라 아무것도 바뀌지 않는다. 그래도 "탐지→제안→승인→집행" 전체가 실 API로 한 바퀴 돈다.

- 위험 0(변경 없음), 이미 코드 존재 → 새로 짤 것 없음.
- App Review에서 `ads_management`를 정당화하는 근거 — pause·예산조정을 validate 모드로 호출하는 화면을 시연하면 쓰기 엔드포인트 사용 증거가 된다.

### 2단계 (제품 가치) — 오가닉↔광고 비교 결과를 쓰기 액션으로 연결

🅰가 만든 comparison 산출물(`LiftResult`)을 보여주고 끝내지 말고 액션으로 흘려보낸다.

**경계 사실 (확인됨)** — `ActionProposal`은 "🅱 단독 생산 / 스튜어드 🅱 / 필드 [확정: 변경 없음]"(`contracts/schemas.py`)이라 🅰가 직접 만들면 위반이다. 또 `AnomalyType` enum엔 "오가닉 위너·광고 효율" 항목이 없어, 진단(`DiagnosisResult`)으로 흘리려면 공유 `enums.py`(🤝) 변경 → A/B 합의가 필요하다. 따라서 연결은 **🅰가 권고 신호만 내고, 🅱가 그 신호를 읽어 `ActionProposal`로 감싸는** seam으로 나눈다.

**🅰가 이미 만든 것 (seam)** — comparison 서브패키지(🅰-로컬, 공유 contracts 무변경)
- `comparison/schemas.py` — `RecommendedAction`(SCALE_UP/HOLD/PAUSE) + `ComparisonRecommendation` DTO
- `comparison/recommend.py` — `recommend_action(lift)` 순수 함수
- 매핑 — `PASS → SCALE_UP`(`suggested_action_type="INCREASE_BUDGET"`) / `CAUTION → HOLD`(힌트 없음) / `FAIL → PAUSE`(`"PAUSE_CAMPAIGN"`)
- `suggested_action_type`은 공유 `TIER_POLICY` 키의 **힌트일 뿐**(정보 방화벽) — Tier 판정·제안 생성은 🅱 책임

**🅱가 이어받을 것** — `ComparisonRecommendation`을 입력으로 `ActionProposal` 생성
- `recommended_action`/`suggested_action_type`을 보고 `action_type` 확정, `target_object_ids`·예산 필드·`expected_state_version` 채움.
- `evidence_metrics`에 `reach_lift_ratio`·`rationale` 등 근거 적재(이미 `executor.py`의 CREATE_CAMPAIGN가 evidence를 받는 구조).
- Tier 판정은 `approval.py`(🅰)/`policy.py`(🤝)가 정본 — 힌트와 충돌 시 정책표 우선.

"분석만 하는 대시보드"가 "분석 → 권고 → 근거 있는 제안"으로 올라간다. CLAUDE.md의 "직감보다 나은 의사결정 근거" 목표와 일치하고, 사람이 승인하므로 exploratory 원칙도 유지.

### 3단계 (베이스라인 이후) — 안전한 쓰기부터 LIVE 해금

LIVE는 한 번에 다 풀지 말고 되돌릴 수 있고 위험을 줄이는 액션부터.

1. `PAUSE_CAMPAIGN` — 지출을 멈추는 방향이라 제일 안전 (Tier-3 건별 사람 승인 유지).
2. `DECREASE_BUDGET` — 줄이는 쪽.
3. 그다음에야 `INCREASE_BUDGET` / `CREATE_CAMPAIGN`.

`executor.py`의 `DEFAULT_ALLOWED_MODES`에 LIVE 추가 + `use_mock` 이중게이트 해제라는 단일 지점에서만 제어돼 통제된 해금이 가능.

## 3. App Review 권한 영향

읽기 전용이면 `ads_management`를 빼는 게 맞지만, 쓰기 루프를 활성화할 거면 반대로 넣어야 한다.

| 권한 | 처리 | 이유 |
| --- | --- | --- |
| `ads_management` | 넣기 | pause·budget·create 쓰기. VALIDATE_ONLY로 시연 가능 |
| `ads_read` | 넣기 | 성과·spend 읽기 |
| `instagram_manage_insights` · `instagram_basic` · `pages_show_list` | 넣기 | 오가닉 비교 |
| publish / messages / comments / manage_posts | 빼기 | 코드상 호출 없음 |

`ads_management` 검수는 까다로우니, 시연 영상에 승인 단계 + 예산 하드캡 + 감사로그가 보이게 하면 통과율이 오른다(검수자가 "통제된 쓰기"를 확인하고 싶어함).

---

## 4. 🅱 검토 포인트

- 1단계 VALIDATE_ONLY 활성화 시점 — 베이스라인 시연에 포함할지.
- 2단계 제안 생성 위치 — **결정됨**: 🅰는 `ComparisonRecommendation` seam까지, `ActionProposal` 생성은 🅱. 🅱가 이 DTO를 입력으로 받는 제안 빌더의 진입점만 정하면 된다.
- `AnomalyType`에 비교용 항목을 추가해 `DiagnosisResult` 경로로 합칠지 여부 — 공유 `enums.py` 변경이라 A/B 합의 필요(현재는 seam DTO로 우회).
- 3단계 LIVE 해금은 별개 의사결정 — KRW 단위는 확정됐으나 LIVE writer 봉인은 그대로.
- App Review 제출 전 권한 목록 최종 확정은 🅱·🅰 합의 후.
