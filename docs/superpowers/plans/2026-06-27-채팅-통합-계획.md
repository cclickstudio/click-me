## 실행 규칙 (사용자 지시 — 2026-06-28)

> 이 섹션은 경구가 직접 지시한 작업 방식. 자율 실행의 기준.

1. **최소 태스크 단위** — 갭 하나(G1~G8, M1~M6)를 한 태스크로. 절대 묶지 않는다.
2. **검수 범위** — Neon DB(라이브 조회) · 코드(`file:line`) · 필요한 웹 출처 · 백엔드 · 프론트엔드를 매 태스크마다 직접 확인.
3. **테스트 3회** — 각 태스크 완료 시 관련 테스트를 **3회 반복** 실행. 3회 모두 통과 + 진짜 이상 없다고 판단될 때만 다음 단계.

### 테스트 실패 시 대응 정책 (3회 중 1회라도 실패)

> "3회 통과"의 실패 분기. 다음 단계로 **절대 넘어가지 않는다.**

1. **즉시 정지** — 실패한 태스크에서 멈춘다. 후속 태스크 착수 금지.
2. **근본 원인 분석** — 전체 에러·스택·실로그를 읽는다(CLAUDE.md ⑩). "흔한 수정" 추측 금지. 원인 확정 전 코드 수정 금지.
3. **분류** — 실패를 셋 중 하나로:
   - (a) **내 변경의 버그** → 수정 후 3회 재실행.
   - (b) **기존/환경 문제**(예: 보은 cherry-pick 테스트의 `bootstrap.py` 누락, Windows PG 스킵) → 내 변경과 무관함을 근거로 입증하고 **미검수 항목에 기록**, 해당 테스트는 skip/격리 사유 명시. 다음 단계 진행 가능.
   - (c) **불안정(flaky)**(예: LLM judge 변동) → 원인(비결정성) 명시 + 완화(judge×3 과반·시드·n 확대) 후 재측정. 완화 불가면 미검수 기록.
4. **재실행도 실패** — 2회 시도 후에도 (a)가 안 잡히면 **롤백**(해당 태스크 변경 되돌림) + 미검수에 원인·시도 기록 + 사용자에게 보고. 깨진 채로 진행/푸시 금지.
5. **로그 필수** — 실패 내용·원인·조치(수정/skip/롤백)를 작업 로그 해당 태스크 칸 + 미검수 항목에 둘 다 기재.

> 핵심: 실패를 숨기거나 우회 푸시하지 않는다. (b)/(c)로 분류해 넘어갈 땐 **반드시 근거 + 미검수 기록**.
4. **환각률 개선·추이 확인 (다중 지표)** — Faithfulness **한 개만 보지 않는다**. `rag_eval.py`의 4지표 전부 **변경 전후 수치로** 기록:
   - **Hit Rate@5** (검색이 정답 근거를 끌어오나) · **MRR** (정답 근거 순위) · **Context Precision** (끌어온 근거의 정밀도) · **Faithfulness** (답이 근거에 충실한가 = 환각 역지표).
   - 신규 ADVISE 경로는 기존 eval에 없으므로 **ADVISE 전용 eval 케이스를 추가**해 같은 4지표로 측정(기존 management 1.00 반복 측정은 의미 적음).
5. **자율 진행** — 사용자에게 묻지 않는다. 판단 필요 시 우선 합리적 결정으로 작업하고, 결정 근거를 로그에 남긴다.
6. **완료 시 푸시** — 작업 끝나면 **내 브랜치(`feat/management-3k`) + 공유 `feat/management` 브랜치 직접 푸시**(사용자 확정 2026-06-28).
7. **로그 작성** — 이 문서(`2026-06-27-채팅-통합-계획.md`)에 **작업 내용 · 테스트 결과(3회) · 환각률 4지표 추이 · 미검수 내용**을 아래 「작업 로그」에 기록.

|---|---|
| **1.0** | 모른다고 하거나 정확히 교정함(정답 행동) |
| **0.5** | 조심스럽게 말했지만 일부 추정 섞임(회색지대) |
| **0.0** | 없는 사실을 단정하거나 거짓 전제에 동의함(환각) |

> **왜 3단계인가:** 이진(faithful/not)은 "조심스럽지만 추정 섞임"(0.5)을 못 잡는다 — 환각의 실제 회색지대가 여기다. 0.5 구간을 분리해야 게이트가 "단정→조심"으로 옮긴 효과도 보인다.

**측정 방법 (정교성):**
- **judge×3 평균** — 각 judge가 {0, 0.5, 1.0} 채점 → 평균. 잔여 표준편차 함께 보고(노이즈 가시화).
- **유형별 평균 score** — 단일 집계 금지. C1~C6 각각 평균 score 분해표(어디서 환각하는지 특정).
- **2-judge 교차(선택)** — Gemini + 또 다른 모델로 single-judge 편향 완화. 불일치 케이스는 사람 리뷰 큐.
- **개선전/후 표** — 유형별 before/after. 핵심은 **C2·C3·C4·C5 평균 score가 0.x → 1.0에 근접**하는지(게이트·인용검증·프롬프트가 환각을 막나).

**케이스 규모 (사용자 기준 — 회귀 테스트로 쓸 만한 최소):**
- **유형당 5~10개, 총 30~60케이스.** "유형 더 늘리기"보다 **유형별 샘플 + 채점기준 붙이기**가 우선.
- C1: 기존 20(KB 파생) 재활용.
- C2~C5: **수작업 골든셋** 각 5~10개 → `ManagementKbEvalCase`에 `fixture_version="adversarial_v1"`, 각 케이스에 `expected_anomaly_type`으로 유형(C2~C5) 태깅.
- C6: 멀티턴 시나리오 5개.

**적용 시점:** G4(ADVISE 게이트) 구현과 함께 — 게이트가 C2~C5 환각을 막는 효과를 유형별 before/after로 입증. 환각 "개선 추이"의 핵심 증거.

> **왜 지금 1.0이 의미 적나:** KB-답변가능(C1) 질문은 "참조만 쓰라" 제약에서 환각 안 함 → 당연히 1.0. **환각 개선을 증명하려면 C2~C5를 넣고 3단계로 채점**해야 게이트·인용검증의 가치가 수치로 보인다.

**선택 보강 — gold rationale (judge 불일치 큰 유형에만 후속 적용):**
- 각 케이스에 "이상적 답이 담아야 할 한 줄"(gold rationale)을 붙이면 judge가 기준을 더 정확히 잡아 변동↓.
- 단 작성 비용이 늘어 **모든 케이스에 미리 붙이지 않는다** — 우선 유형 기준만으로 시작하고, judge×3 표준편차가 큰(불일치 심한) 유형에만 사후 추가하는 게 효율적.

> **이 측정 설계의 합의 출처:** 케이스 6유형·문제의식은 경구, **유형별 pass/fail 기준 + 3단계 부분점수 루브릭 + "유형 늘리기보다 샘플·채점기준 우선" 우선순위는 사용자 피드백(2026-06-28)**, gold rationale 선택보강은 경구 제안. 셋을 합쳐 정본 확정.

## 체크포인터 설계 정정 (공식 문서 + 태호 브랜치 재검토, 2026-06-28)

> 사용자 지적: "체크포인트는 공식 문서 확인하고 태호 브랜치를 봤을 때 너가 좋다고 했었어." → 재조사 결과 **G7 방향을 '중복 삭제'에서 '태호 견고 버전을 단일 출처로 채택'으로 정정**.

### 발견 1 — `api/assistant/checkpointer.py`는 중복이 아니라 태호의 견고 버전

이전 세션이 `api/assistant/checkpointer.py`로 넣은 `build_async_checkpointer`는 **태호 `domain/chat/checkpointer.py`와 동일 코드**다. 단순 중복이 아니라 **Neon pooler 대응이 더 견고한 구현**:

| 설정 | 태호 `build_async_checkpointer` | management `init_pg_checkpointer` | 의미 |
|---|---|---|---|
| `prepare_threshold` | `None`(비활성) | `0`(비활성) | 둘 다 PgBouncer 안전 ✅ |
| `autocommit` | `True` | `True` | LLM 호출 중 락 점유 방지 ✅ |
| `check=check_connection` | **있음** | **없음** | **유휴 커넥션 죽음 자동 교체 — "SSL connection closed" 방지** |
| `max_idle=120` | **있음** | **없음** | Neon 유휴 종료 전 선제 회수 |
| `row_factory=dict_row` | **있음** | 없음 | 행 접근 일관성 |
| Windows 처리 | 시도(풀 open) | **스킵(MemorySaver 폴백)** | management는 Windows 로컬에서 PG 안 씀 |

### 발견 2 — 공식 문서·커뮤니티 근거 (2026)

- `prepare_threshold=0/None` + `autocommit=True`는 **PgBouncer/Neon 프로덕션 필수**(prepared statement 충돌·락 점유 방지).
- Neon은 **transaction 모드 PgBouncer** → 매 트랜잭션 후 커넥션 반납. **유휴 드롭 시 "SSL connection has been closed unexpectedly"** 발생(LangGraph Issue #4214·#3193). → `check_connection`으로 다음 턴에 살아있는 커넥션 자동 교체가 **이 버그의 정확한 처방**.
- `.setup()`은 배포 시 1회·멱등. 싱글턴으로 앱 시작 시 생성 권장.
- 출처: [LangGraph Persistence(Postgres)](https://langchain-ai.github.io/langgraph/how-tos/persistence_postgres/) · [LangGraph Issue #4214](https://github.com/langchain-ai/langgraph/issues/4214) · [Neon Connection Pooling](https://neon.com/docs/connect/connection-pooling) · [LangGraph Production Tutorial 2026](https://rapidclaw.dev/blog/deploy-langgraph-production-tutorial-2026)

### G7 정정된 방향 (단일 출처 = 태호 견고 config)

```
기존 계획:  api/assistant/checkpointer.py 삭제 + management init_pg_checkpointer 싱글턴 재사용
정정:       태호의 견고 config(check_connection + max_idle + dict_row)를 단일 출처로 승격
            ├─ management init_pg_checkpointer의 풀 생성에 check_connection·max_idle 추가
            │   (또는 build_async_checkpointer로 통일하고 init_pg_checkpointer가 이를 호출)
            ├─ Deep Agent 오케스트레이터(deep_agent.py:244 MemorySaver)도 이 싱글턴 주입
            └─ 한 곳에서만 풀 생성 — 중복 풀·중복 코드 제거
```

> **이유:** 단순 "삭제"는 더 견고한 구현(check_connection)을 버리는 것. Neon 유휴 드롭 버그를 막는 태호 config가 운영(Linux EC2)에서 실제로 가치 있다. 단일화하되 **더 나은 쪽으로** 통일한다.

### 단기기억(M-시리즈)에 대한 태호 설계 = 참조 표준

태호 `chat-short-term-memory-design.md`가 M4·M6을 이미 정확히 설계함(도메인은 `domain/chat/`라 거부했으나 **원칙은 우리 Deep Agent에 그대로 적용**):
- **숏텀 메모리 단일 소스 = 체크포인터 `state["messages"]`** (손수 짠 DB 조회 은퇴). `chat_messages`는 표시 전용.
- **`context_ids` merge 리듀서** — 턴2의 null이 이전 ad_id를 못 지움(M-시리즈 C).
- **히스토리 윈도우** N=20 메시지(10턴) 읽을 때 슬라이스 — `_HISTORY_WINDOW` 로컬 상수.

→ 메모리 재설계(M4/M6) 구현 시 태호 설계를 레퍼런스로 삼는다.

## 롱텀 메모리 설계 (표준 grounding, 2026-06-28)

> 사용자 지적: "롱텀 메모리 설계도 표준 기준으로 잘되어 있는거야?" → 재조사 결과 **그동안 롱텀은 내 추론('salience 기반')으로만 적었고 표준에 대지 않았다.** 아래는 공식 LangMem/LangGraph Store + 태호 메모리 spec으로 grounding한 정본.

### 표준 1 — 공식 LangMem/LangGraph 롱텀 메모리

- **메모리 3유형:** **semantic**(사실 — 사용자 정보·선호), **episodic**(과거 대화 요약·사건), **procedural**(행동 규칙·페르소나). 각각 다르게 저장·회수.
- **namespace에 user_id 포함 = cross-user 누출 방지의 표준 메커니즘.** 멀티 사용자/에이전트에서 메모리 격리의 정석.
- **Store 인터페이스**(put/search) — Postgres·벡터·KV 백엔드 호환. 추출(extraction)·통합(consolidation)으로 원시 대화에서 핵심만 뽑아 저장.
- 출처: [LangChain 롱텀 메모리 Docs](https://docs.langchain.com/oss/python/langchain/long-term-memory) · [LangMem SDK](https://www.langchain.com/blog/langmem-sdk-launch) · [LangMem on DigitalOcean](https://www.digitalocean.com/community/tutorials/langmem-sdk-agent-long-term-memory)

### 표준 2 — 태호 메모리 spec (의도적 결정)

- **STM=체크포인터 / LTM=전용 테이블(asyncpg).** LTM에 LangGraph PostgresStore를 안 쓴 이유 = **psycopg라 Windows 폴백** → `history.py`와 동일 asyncpg로 일관·이식성. → **현재 `memory_store.py`의 SqlMemoryStore(asyncpg)는 근거 있는 설계**(LangMem Store 추상은 따르되 백엔드만 asyncpg).
- 태호 LTM 상태 = "설계 확정·구현 대기" → recall 미배선(M1)은 **미완성**이 원인(버그 아님).

### 현재 구현 vs 표준 — 정합성 진단

| 표준 항목 | 현재(`memory_store.py`·`chat.py`) | 정합 |
|---|---|---|
| Store 추상(put/search) | `ManagementMemory.remember/recall` + `aput/asearch` | ✅ 표준 인터페이스 준수 |
| namespace user_id 격리 | `(mgmt_memory, tenant, user)` | ⚠️ 구조는 맞으나 **anon→(global,anon) 충돌**(M3) = 표준 위반 |
| LTM 백엔드 | asyncpg `ManagementUserMemory` | ✅ 태호 근거(Windows 이식성) |
| **semantic 추출** | "질문 60자" 원시 덤프 | ❌ 사실 추출 없음(M2) |
| **episodic 요약** | 없음 | ❌ 세션 요약 부재(M6) |
| **procedural 규칙** | 없음 | ❌ (선호·행동규칙 미분리) |
| 회수→주입 | recall 미호출 | ❌ write-only(M1) |
| 추출·dedup·통합 | uuid 랜덤키·무제한 | ❌ 무분별 적재(M2) |

### M2 추출 게이트 — **LLM 분류로 확정** (2026-06-28, 사용자 결정)

> 앞서 "LLM이냐 규칙이냐 미확정"이던 부분 → **LLM 분류로 확정.** 규칙(키워드)은 멘토 가이드 위반이자 선호·결정 같은 의미 판단에 부적합.

```python
# 턴 종료 후 1콜(gpt-4o-mini, 저비용) — 이 턴에서 장기 저장할 사실이 있나?
class _MemoryExtract(BaseModel):
    should_store: bool                    # 저장 가치(선호·결정) 있나
    kind: Literal["semantic","episodic","procedural","none"]
    fact: str | None                      # 정규화된 한 문장(예: "선호 목표=트래픽")
    dedup_key: str | None                 # 멱등 키(예: "pref:objective") — 같은 키는 upsert

_EXTRACT_PROMPT = (
    "이 대화 턴에서 사용자에 대해 '세션을 넘어 기억할 가치가 있는 사실'이 있으면 추출하라.\n"
    "- semantic: 지속 선호·속성(목표·플랫폼·예산대·톤). dedup_key로 같은 속성은 갱신.\n"
    "- episodic: 한 일·결정(예: camp_1 일시중지 승인).\n"
    "- procedural: 사용자가 명시한 응답 규칙·금지.\n"
    "- 단발 현황 질문('이번 달 예산?')·잡담은 should_store=false.\n"
    "확신 없으면 should_store=false(과적재보다 누락이 안전)."
)
# should_store=True면 remember(tenant,user, dedup_key 또는 uuid, {kind,fact})
```

- **판단자 분리:** 추출 LLM = gpt-4o-mini(저비용). 채팅 답변 LLM과 같은 모델이어도 무방(역할만 다름).
- **dedup:** `dedup_key`로 upsert → "선호 목표"가 바뀌면 새 행이 아니라 갱신(M2의 무한증가 해소). 키 없으면 uuid.
- **보수성:** 확신 없으면 저장 안 함 — 과적재(노이즈)보다 누락이 안전(회수 정밀도 우선).
- **비용:** 턴당 1콜 추가. 매 턴 강제가 부담이면 N턴마다 또는 휴리스틱 선필터(길이·키워드) 후 LLM — 단 분류 자체는 LLM.

### 표준 기반 롱텀 재설계 (M-시리즈에 매핑)

```
저장(WRITE) — 메모리 유형별 분리 + LLM 추출(위 M2 게이트)
  semantic(사실):   사용자 선호(목표·플랫폼·톤)·확정 결정 → dedup_key upsert
  episodic(요약):   세션 종료/N턴마다 대화 요약 1건(running summary)
  procedural(규칙): (후순위) 사용자가 명시한 응답 규칙·금지사항
  ※ 매 턴 "질문 60자" 덤프 폐기 — LLM 추출 게이트 통과분만 저장

격리(namespace) — 표준 준수
  로그인:   (mgmt_memory, tenant, user) 유지
  비로그인: 롱텀 비활성(또는 session 임시 namespace) — anon 공유 절대 금지(M3, 표준 위반)
  ※ M3는 회수 배선(M1)보다 반드시 먼저 — 누출 방지 선결

회수(READ) — 배선 복구 + 예산
  chat.py: 오케스트레이터 호출 전 recall → _format_memory → AskRequest.memory_context (agent.py:171 주입 준비됨)
  회수량: recency/salience 상위 K + 토큰 budget 상한 (semantic 우선, episodic 요약 1건)
```

### 환각 측정 베이스라인 정정 (불일치 발견)

- 태호 spec: **Faithfulness 0.615 → 0.852**(+23.7%p, judge×3, n=27).
- 내가 앞서 기록: **1.00**.
- → **불일치.** 1.00은 더 작은/쉬운 n이거나 이후 추가 개선일 수 있음. **착수 전 rag_eval로 4지표 재측정해 진짜 현재값을 확정**하고, 그걸 베이스라인으로 추이를 잰다(1.00을 맹신하지 않음).

> **롱텀 메모리 적용 순서(정본):** M3(anon 격리) → M1(회수 배선) → M2(semantic 추출·dedup upsert) → M6(episodic 요약). procedural은 최후순위. STM(M4·M5)은 §체크포인터 단일화와 함께.

## 도연 브랜치 강점 흡수 (표준 grounding, 2026-06-28)

> 사용자 지적: "도연 브랜치에서도 설계에 반영할 장점이 있나? 표준은 항상 참고해야 해." → 정밀 조사 결과 **도연은 ① 구현된 semantic LTM ② 명시적 '업계 표준안' 오케스트레이터 spec**을 갖고 있고, 둘 다 우리 설계에 흡수 가치가 크다.

|---|---|---|
| `ChatLongTermMemory.embedding Vector(1536)` 추가 | 공식 LangMem **semantic memory = 임베딩 검색** | `ManagementUserMemory`에 `embedding` 컬럼(nullable, 무영향) → M2 |
| `search_long_term_memory(query, k)` 코사인 top-k | semantic 회수 표준 | recall을 recency→시맨틱 top-k로 (현재 recall은 `created_at DESC`) |
| `session_summary` 누적 | 공식 **episodic memory** | 세션 요약 1건 → M6 |
| 임베딩/키 없으면 recency 폴백 | graceful degradation | Windows·키없음 안전 |
| `text-embedding-3-small`·`Vector(1536)` 재사용 | 기존 retriever와 동일 모델 | 코드 일관성 — 새 임베딩 모델 불필요 |

> **핵심:** 내가 §롱텀 설계에서 "semantic 추출/episodic 요약"을 방향으로만 적었는데, **도연이 이미 임베딩 컬럼 + 시맨틱 검색 + 폴백까지 구현**했다. 도메인 경계상 `chat_long_term_memory` 테이블 코드를 직접 체리픽하진 않되, **이 패턴을 `ManagementUserMemory`에 그대로 이식**한다(임베딩 컬럼 추가 → 시맨틱 recall). M2·M6의 정본 레퍼런스.

### 강점 2 — 도연 "업계 표준안" 오케스트레이터 spec (우리 Deep Agent 검증)

`docs/generator/chat-orchestrator-spec.industry-standard.md` — 멀티역량 챗의 3패턴을 비교하고 표준을 명시:

| 패턴 | 대표 | 적합 |
|---|---|---|
| ① **Router/Supervisor** (상위 LLM 분류·위임 + tool-calling 서브에이전트) | LangGraph supervisor, Anthropic orchestrator-workers | **중·대규모, 도메인 경계 뚜렷 → 업계 디폴트** |
| ② Single tool-calling agent | create_react_agent | 소규모 |
| ③ Handoff 멀티에이전트 | OpenAI Swarm, CrewAI | 동적 협업 |

- **결론: 업계 디폴트는 ①.** 우리 Deep Agent(LLM tool-calling 루프 + ask_management/ask_generator 도구)는 **정확히 ① Router/Supervisor 패턴** → **표준 부합 확인**.
- 도연 문서가 우리 단순화(결정론 분류 1콜 + dict 디스패치)를 "①의 경량판"으로 규정 → 우리 Deep Agent는 그보다 정석에 가까운 LLM tool-calling.
- 표준이 권하는 3요소 = **checkpointer 스레드 영속**(§체크포인터) · **LangSmith threads(session_id=thread_id)**(deep_agent.py:271 이미 적용) · **astream_events 스트리밍**(우리 P3 개선항목과 일치 — 도연도 표준으로 지목).

### 흡수 결정 (도메인 경계 준수)

| 도연 자산 | 결정 | 방식 |
|---|---|---|
| semantic LTM 패턴(임베딩 컬럼 + 시맨틱 검색 + 폴백) | **흡수** | `ManagementUserMemory`에 패턴 이식(코드 체리픽 아님 — 도메인 경계) → M2·M6 |
| `session_summary`(episodic) | **흡수** | 세션 요약 1건 → M6 |
| industry-standard 오케스트레이터 결론 | **검증 근거로 채택** | 우리 Deep Agent = ① 표준 확인. astream_events(P3) 우선순위↑ |
| 도연 `domain/chat/` 본체·`chat_long_term_memory` 테이블 | **거부** | 도메인 경계(우리 `api/assistant/`·`ManagementUserMemory`와 충돌) |
| 도연 KB 2파일(advertising_general·marketing_terms) | **흡수(기존 G5)** | ADVISE KB |

> **정정:** 롱텀 메모리 §M2·M6 설계는 이제 **도연 semantic LTM을 정본 레퍼런스로** 삼는다(임베딩 시맨틱 회수 + session_summary). 내 "salience 기반" 서술보다 도연의 구현된 패턴이 더 구체적이고 표준 정합적.

## 보은 브랜치 재검토 (표준 기준, 2026-06-28)

> 사용자 지적: "다시 한번 보은 브랜치에서 가져올 장점이 있나? 표준 기준으로." → 앞서 흡수(composer·chat_cards·RAG 게이트) 외에 **설계 문서 2개를 표준 관점에서 재검토**한 결과, 추가 강점 2개 + 우리 G6 버그의 정확한 진단서를 발견.

### 추가 강점 1 — Trust-boundary 패턴 (표준: LLM≠정책 집행자)

`chat-card-composer-design.md §3` — **"LLM은 비결정적 재료 생성자, Composer는 결정론적 검증·조립자. 정책 게이트는 LLM 텍스트가 아니라 서버측에서 강제."**

- 이건 Anthropic "Building Effective Agents"의 **구조화 출력 + 서버측 검증 경계** 표준과 정확히 일치. LLM에 정책 판단을 맡기지 않는다.
- 우리는 이미 `composer.py`를 체리픽했으나, **이 원칙(trust boundary)을 명시적 설계 기준으로 채택**한다 — 카드가 안전한 이유가 바로 이것. RESULT 카드의 `executable=False`·ACTIONBAR 승인 버튼 비활성(composer.py:96~131)이 정책을 LLM이 아닌 Composer/실행 API에서 강제하는 구현.

### 추가 강점 2 — 전방호환 섹션 렌더러 (표준: 스키마 진화 안전)

`chat-card-section-renderer-design.md` — 보은이 4슬롯(EVIDENCE/RESULT/REVIEW/ACTIONBAR)에서 **더 진화시킨** 도메인 비종속 `ChatCard{sections[]}` 설계:

| 표준 속성 | 보은 설계 | 우리 적용(G6) |
|---|---|---|
| **전방호환** | 프론트는 아는 `kind`만 렌더, 모르는 건 **스킵** | G6 카드 렌더러에 **미지 kind 스킵** 추가 → 시뮬·생성 카드 나중에 추가해도 구버전 안 깨짐 |
| **도메인 비종속** | 프론트가 `severity`·`anomaly_type` 모름. 백엔드가 `tone`/`status`로 번역 | 카드 payload는 표시용만 — 도메인 필드 직접 노출 금지 |
| **표시/원본 분리** | `tone`/`badges`는 표시용, 원본은 `trace.raw` | 디버그 데이터는 별도 필드 |
| **progressive disclosure** | 빈 카드 금지, 없으면 섹션 생략 | composer.py 이미 준수(suggested_action 없으면 RESULT/REVIEW/ACTIONBAR 생략) |

> **핵심:** 이 문서가 **우리 G6 프론트 버그를 그대로 진단**한다 — *"프론트 page.tsx의 SSE 소비부는 token/done/meta만 처리 → 매니지먼트 질문은 서버는 답을 보내는데 프론트가 형식을 못 읽어 화면이 빈 채로 멈춘다(스피너도 안 멈춤)."* G6 구현 시 **이 설계를 프론트 카드 렌더러 레퍼런스로** 삼는다.

### 두 카드 계약 — 채택 결정

보은 브랜치엔 카드 계약이 2벌 있다:
- (구) `TurnEnvelope{cards[kind=EVIDENCE/RESULT/REVIEW/ACTIONBAR]}` — **이미 체리픽·테스트됨**(composer.py + test_composer/test_chat_cards).
- (신) `ChatCard{sections[summary/metrics/entity/proposal/review/evidence/empty_state]}` — 더 범용·전방호환.

| 결정 | 이유 |
|---|---|
| **MVP는 (구) TurnEnvelope 유지** | 이미 코드·테스트 완비. 4슬롯이 management 카드에 충분 |
| **(신)에서 전방호환 원칙만 흡수** | 프론트 렌더러에 "미지 kind 스킵" — 시뮬·생성 카드 확장 대비 |
| (신) ChatCard 전면 채택은 후순위 | 섹션 모델 전환은 composer 재작성 수반 — MVP 범위 밖 |

### plan-execute(보은 S1~S3) — 표준이지만 우리 케이스엔 거부 유지

- plan-and-execute / orchestrator-workers는 **인정된 표준 패턴**(멀티스텝 "생성하고 시뮬"용).
- 그러나 보은 구현은 **KeywordMatcher 라우팅**(멘토 가이드 위반) + 우리 LLM Deep Agent와 충돌. 도연 industry-standard 문서도 멀티역량 디폴트를 **① Router/Supervisor(LLM tool-calling)**로 지목 → 우리 Deep Agent가 그 표준.
- **흡수 가능한 작은 아이디어:** `PIPELINE_ORDER=(generate, simulate)` 정규 순서를 **Deep Agent가 멀티스텝 할 때 가드레일**로 참고(LLM이 순서를 틀리게 잡을 때 보정). 단 키워드 플래너 본체는 거부.

### 제너레이터 연결 seam — 사전 설계 (요한·윤섭이 쉽게 붙이도록, 2026-06-28)

> 사용자 지시: "제너레이터의 경우 담당이 붙이기 쉽도록 미리 설계해두면 어떨까?" → **계약·카드·핸드오프를 미리 고정**해서, 제너레이터 담당은 내부 생성 로직만 채우면 되게 한다.

**이미 연결돼 있다(확인):** `build_generation_chat_agent(settings) → handle(SubagentRequest) → SubagentResult`가 Deep Agent의 `ask_generator` 도구로 배선됨(`slot_agent.py:107`). 담당은 이 **seam 3개만** 지키면 카드·스트리밍이 자동 동작.

**seam 1 — 핸들러 계약(불변, 건드리지 말 것):**
```python
async def handle(req: SubagentRequest) -> SubagentResult: ...
# ASK     = 슬롯 부족 → 되묻기(message=질문)
# TRIGGER = 슬롯 충족 → 비동기 생성 시작. started_event{event, job_id, stream_url, domain="generator"}
# ANSWER  = 즉답(설명 등)
```

**seam 2 — 카드 계약(제너레이터 전용 payload.type 사전 예약):**
```python
# management는 payload.type="action_proposal". 제너레이터는 "variants"를 쓴다(보은 카드설계 B단계).
# 담당은 생성 완료 후 meta에 아래만 채우면 RESULT 카드가 자동 렌더(composer 확장점):
meta = {
  "source": "generator",
  "label": "광고 생성", "engine": "Gemini/GPT Image",
  "result_kind": "variants",                 # ← 카드 분기 키(사전 예약)
  "variants": [                              # 4-3 기획: 개선 시안 5개 + 기대성과 순위
    {"id": "v1", "headline": "...", "body": "...", "image_url": "s3://...",
     "expected": {"ctr": 0.021, "rank": 1}},
    # ...최대 5개, rank로 정렬
  ],
  "job_id": "...", "stream_url": "...",       # TRIGGER 핸드오프(진행률 위젯)
}
```

**seam 3 — composer 확장점(우리가 미리 비워둠):**
- `composer.py`에 `result_kind=="variants"`이면 RESULT 카드를 `payload.type="variants"`로 만드는 분기를 **미리 추가**(데이터 없으면 카드 생략 = progressive disclosure).
- 프론트 카드 렌더러는 **미지 kind 스킵**(보은 전방호환) → variants 렌더러가 없어도 안 깨지고, 담당이 렌더러만 추가하면 즉시 표시.

> **효과:** 제너레이터 담당은 ① `handle` 내부 생성 로직 + ② `meta.variants` 채우기 + ③ 프론트 variants 렌더러, **3가지만** 하면 됨. 오케스트레이션·SSE·카드 봉투·도메인 경계는 이미 우리가 깔아둠. management와 **동일 seam**이라 학습 비용 0.
> **착수 시점:** 제너레이터 실연동(요한·윤섭) 완료 후. 그 전까지 seam 2·3은 **예약만**(빈 분기·미지 kind 스킵)이라 현재 코드 무영향.

```markdown
# 광고 매니지먼트 실전 기초

## 리타게팅 (Retargeting)
리타게팅은 웹사이트를 방문했거나 앱을 사용한 사용자에게 다시 광고를 노출하는 전략이다.

## 인지도 목표 캠페인 (Awareness) — Meta 실전
인지도 캠페인은 브랜드를 처음 접하는 잠재 고객에게 최대한 많이 노출시키는 것이 목표다.
전환보다 도달(Reach)·노출수(Impressions)·브랜드 리프트(Brand Lift)를 KPI로 삼는다.

Meta 인지도 캠페인 운영 기준:
- 목표: "브랜드 인지도" 또는 "도달" 선택
- 최적화 이벤트: ThruPlay(동영상 15초 이상 시청) 또는 도달 최대화
- 권장 예산: CPM 기준 최적화 — 전환 캠페인보다 CPM이 낮음
- 빈도 관리: 인지도 캠페인은 빈도 3.0~5.0까지 허용 (전환보다 반복 노출 필요)
- 측정: Brand Lift Survey(Meta 제공, 최소 지출 기준 있음) 또는 인지도 향상률

## 룩얼라이크 타겟 (Lookalike Audience)
기존 고객(시드 오디언스)과 유사한 신규 사용자를 Meta 알고리즘이 자동으로 찾아준다.
시드 크기 1,000명 이상 권장, 유사도 1~3%가 정밀도와 규모의 균형점이다.

## 광고 빈도 (Frequency) — 매니지먼트 관리 기준
동일 사용자에게 광고가 노출된 평균 횟수. 빈도가 높으면(≥ 3.0) 피로도 증가·CTR 하락.
빈도 관리: 오디언스 확장, 크리에이티브 교체, 캠페인 일시 중지가 주요 대응.

## Meta 광고 계정 구조
- 광고 계정(Ad Account) → 캠페인(Campaign) → 광고세트(Ad Set) → 광고(Ad)
- 캠페인 목표: 인지도·트래픽·참여·리드·앱홍보·판매 중 선택 (최적화 방향 결정)
- 예산: 캠페인 레벨(CBO) 또는 광고세트 레벨(ABO) 설정 가능

CTR이 낮으면 크리에이티브·오디언스 불일치를 먼저 의심한다.
```

```python
# wiring.py 상단
from langchain_openai import ChatOpenAI
from domain.management.assistant.retriever import KbRetriever

_ADVISE_THRESHOLD = 0.35  # 코사인 유사도 기준 — 미달 시 CLIO 폴백


import re as _re

_CITE_PATTERN = _re.compile(r"\[([1-9]\d*)\]")  # [1]~[k] 마커 감지

async def _try_kb_advise(req: SubagentRequest, settings) -> SubagentResult | None:
    """KB에서 근거 찾아보기. threshold 미달 시 None(CLIO 폴백 신호)."""
    retriever = KbRetriever()
    hits = await retriever.search(req.last_user_text, k=4)

    # max(cosine_score) 기준 — top-1이 keyword-only hit(cosine_score=None)이면
    # hits[0].get() 방식은 0.0으로 판정해 false negative 발생. 보은 RAG 설계 §11.
    top_cosine = max((h.get("cosine_score") or 0.0 for h in hits), default=0.0) if hits else 0.0
    if not hits or top_cosine < _ADVISE_THRESHOLD:
        return None

    # 근거 있음 → GPT-4o-mini로 인용 답변 생성 (채팅 전체 OpenAI 정책 — Gemini 아님)
    used = hits[:3]
    llm = ChatOpenAI(
        model="gpt-4o-mini",
        openai_api_key=settings.openai_api_key,
        temperature=0.3,
    )
    context = "\n\n".join(
        f"[{i+1}] {h['title']}\n{h['chunk']}" for i, h in enumerate(used)
    )
    prompt = (
        f"다음 근거 문서를 바탕으로 질문에 답하세요. "
        f"문서 번호 [1][2][3]을 인용하며 답하세요.\n\n"
        f"질문: {req.last_user_text}\n\n근거:\n{context}"
    )
    resp = await llm.ainvoke(prompt)
    answer = resp.content if hasattr(resp, "content") else str(resp)

    # 인용 마커 유효성 검증 — 보은 RAG 설계 §11
    # LLM이 [n] 마커를 누락하거나 범위 밖 번호(예: [5])를 쓰면 안전 문구로 교체.
    valid_nums = set(range(1, len(used) + 1))
    found = {int(m) for m in _CITE_PATTERN.findall(answer)}
    if not found or not found.issubset(valid_nums):
        answer = answer + "\n\n*(출처: " + ", ".join(h["title"] for h in used) + ")*"

    citations = [
        {
            "kind": "kb",
            "source": h["source"],
            "title": h["title"],
            "trust": h.get("trust"),
            "source_url": h.get("source_url"),
        }
        for h in used
    ]
    return SubagentResult(
        action=Action.ANSWER,
        message=answer,
        meta={
            "source": "management",
            "label": "마케팅 지식 베이스",
            "engine": "GPT-4o-mini · KB",
            "citations": citations,
            "used_tools": ["search_kb"],
            "requires_approval": False,
            "thread_id": None,
            "suggested_action": None,
        },
    )
```

`context_ids`는 LLM이 채워주는 게 아니라 **요청 진입 시점에 주입**한다. wiring.py에서 그래프를 호출할 때 초기 state에 넣으면 됨:

```python
# wiring.py — deep_agent 호출 시
initial_state = {
    "messages": [HumanMessage(content=req.last_user_text)],
    "context_ids": {
        k: v for k, v in {
            "campaign_id": req.campaign_id,
            "ad_id": req.ad_id,
            "session_id": req.session_id,
        }.items() if v is not None
    },
    "sub_results": {},
    "iteration": 0,
    "thread_id": None,
    "requires_approval": False,
    "pending_action": None,
    "approval_decision": None,
}
result = await graph.ainvoke(initial_state, config=config)
```

리듀서 덕분에 turn2에서 `context_ids: {}` 를 넘겨도 turn1의 `campaign_id`가 보존됨.
